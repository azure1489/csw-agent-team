## 27. 知识库的实现选型：数量级与 LanceDB 是否合适（9/21）

用户给了自部署的多模态向量与重排服务（文档 `/Volumes/gm2tb/git/qwen3-vl-embedding/Qwen3-VL-Embedding-Public-API.md`，密钥在文档里，不入库）：`https://embedding.aworld.ltd`，`Qwen3-VL-Embedding-2B` 输出 2048 维已归一化向量，文本 / 图片 / 图文融合；`Qwen3-VL-Reranker-2B` 给 0–1 分，支持以文搜图、以图搜文。限制：单 GPU 串行、网关 60 秒超时、每次 ≤32 段文本或 ≤8 张图；图片 0.42 秒/张，重排 0.12 秒/段文本、0.43 秒/张图；图片建议 base64。

**数量级（csw_pgv 直查 + 已建范例）**：判断参考库 = 公众号正式已发布（估 300–350 篇，拆条约 1,500，图约 8,000；csw 库 `wechat_article` 400 篇含草稿、207 篇 status=1；引擎 ledger 51）+ 范例 41 条 / 225 图 + 生成过文章的贴文 1,911 条 / 9,373 图 + Van 勾选 2,044 + 引擎决定几十条，合计约 6,000 条文本、18,000 张图，向量约 24,000 × 8 KB ≈ 190 MB；一次性向量化约 2 小时（图片串行）。若加近 90 天 Instagram 做以图查重：13,197 条 / 63,229 图，再加约 600 MB、7 小时；全部历史 77,783 条 / 349,938 图 ≈ 3.4 GB。每天增量约 180 条、800 图，向量化约 6 分钟；逐条判断前的重排（每条 30 个文本候选）约 11 分钟。csw 库已有 pgvector 2560 维列（另一个文本模型，贴文覆盖 65%），与本服务不兼容。

**结论**：数量级在 10^4–10^5，任何方案都够；LanceDB 在容量、多模态、混合检索上都合适，但官方 SDK 只有 Python / TypeScript / Rust，Go 只有社区 CGO 绑定（`lancedb/lancedb-go`），而引擎与采集服务都是 Go。建议第一期把知识库放在引擎 SQLite 里：结构化表 + FTS5（品牌、产品、别名）+ `sqlite-vec` 向量表（`modernc.org/sqlite` v1.59 起内置，引擎现为 v1.34.4 需升级；暴力 KNN，2 万级向量毫秒级、10 万级零点几秒）+ 图片走引擎 BlobStore（本地 / OSS）。两种情况再换 LanceDB：知识库服务决定用 Python 做（本地 MCP 已是 Python 时最自然），或要把几十万张 Instagram 图全量入库做以图搜图。pgvector 不推荐：2048 维超过 `vector` 索引上限 2000，得用 `halfvec`，且要把我们的表放进 csw 的库。
