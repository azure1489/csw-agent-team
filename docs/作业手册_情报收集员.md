# 作业手册 · 情报收集员

> 这个岗位负责 **01-情报逐条**（按窗口逐条采集，交研究员初筛）、**05-配图与素材核**（选题批准后只为已批条目补齐最终配图与关键事实），以及接入小红书后的 **11-小红书选图包**（按资讯分组的原图、建议顺序与来源记录，不做封面卡与内容卡）。
> 各阶段的「作业内容 / 提交前自检」由引擎定义生成（与 `task <id>` 同源），审核尺子见《资讯日更 · 验收标准》，流程见《资讯日更 · 全流程》，业务约定见《资讯日更 · 生产约定》。

## 全岗位共同条款

- 开工先读：《资讯日更 · 生产约定》有效版本、当期明确范围、最新人审决定、当前交付物与相关历史。岗位记忆不能替代这些记录。
- 已授权范围内的必要核验、改用可用来源、整理文件和修正交接字段，主动推进；只把需要改变范围、取舍或授予新权限的决定交主编。遇到一处缺口，继续其他不依赖它的工作。
- 交付以真实文件和引擎提交为准。重复退回时改变具体处理方法，不以重述要求、延长截止时间或生成自检报告代替修改。
- 已批准内容按版本保持；改动涉及事实、选题或编辑意思时标明受影响范围；不用新文件覆盖已批准对象，换图换资产走补件。
- 本地演练、后台草稿、公开发布是不同授权。只有本地演练授权时，任何下游解锁都不等于可以进后台。
- 引擎是权威：收到派工先接单；做不了就报告失败并写原因；群播报由引擎发，你被 @ 后回引擎核实，不手动转述流转。

## 这个岗位现在由什么在执行

**情报收集员工作台**（`csw-collector`，跑在 agent 主机上的常驻服务）接管了 01 / 05 / 11。
它自己轮询引擎接单、自己干活、自己提交，不再被飞书 @ 唤醒，也不回群。
方案见《情报收集员工作台 · 总方案》，接口见 `csw-task/csw-collector/API.md`。

**岗位标准一个字没变。** 交什么、按什么尺子验收，权威仍然是引擎定义
（`task <id>` 返回的那三段），下面各阶段小节也仍然由它生成。
换掉的只是**谁在执行**，以及随之而来的三件事：

| | 过去（Hermes agent） | 现在（工作台） |
|---|---|---|
| 看多少 | 先扫一遍挑 4–8 条成形的线索交首批 | **窗口内每条图文贴文都判、每张图都识别**；四档结论 + 六维依据全部进台账 |
| 主编闸在看什么 | 首批那几条对不对方向 | 整期台账：模型判了什么、凭什么判；主编在工作台上改档、指定深核首批 |
| 「首批」指什么 | 先交的那 4–8 条情报 | 先深核、先交付的那几条——**判断是全量的，首批只是交付的先后** |

**人在哪里介入**：主编在工作台改档（四档之间挪，理由必填，原判一个字不动）、
指定这一轮深核的首批；Van 在 Van 模式里勾选（like / doubt / note），
但**她改不了档**——进不进评选由主编在引擎上代录并附她的原话。

**回退时这份手册原样生效。** 停掉工作台、把 `hermes-gateway-collector.service`
起回来，Hermes 收集员照着下面各节接着干，部署模板在 `skill/bootstraps/collector.md`。
引擎那边的兼容是现成的：02 / 03 读台账，台账为空就退回 `intake-trace`。

## 岗位要点

- **保留**：可追溯来源、原始发布时间、变更事实、来源去重、配图整理及当期 24 / 72 小时窗口。
- **时间分开写**：原始披露时间与转载时间的差别要保留，晚抓到的旧内容不能改成当天新闻；同品牌新事件能否采用由研究员和主编判断。
- **判断过就不许留在 candidate**：确定不做的标 `dropped` 并给 `reason_code` 与理由，关键事实没核实的标 `pending_check`。**待核不是淘汰**，它第二天仍在窗口里就还要出现在台账上。
- 「昨日提案未发」按真实结果区分：明确否决、待核验、当日容量不足、未决定——不一律当作不喜欢。

以下两条按执行者不同而不同：

| | 工作台 | Hermes agent（回退时） |
|---|---|---|
| **看多少** | 窗口内每条图文都判、每张图都识别。「首批」指先深核先交付的那几条，不是只看了那几条 | 先交成形的 4–8 条等主编校准，再按校准意见补采，新条目以补件追加 |
| **删减** | 不删减：判断是全量的。省的是深核与配图——只有进了推荐 / 备选的才在 05 补三张图 | 候选初筛前不为全部低潜力内容完整下载三图、不复制历史全包；已选条目仍满足最终配图标准 |

## 工具与节奏

**工作台**（当前执行者）：

- Instagram → 直接调 csw 贴文接口（`GET /posts/window` 按窗口取全量、翻页取完），不走 MCP。
- 小红书与网页 → 采集器默认**关闭**。开之前 `intake_sources` 里对应的来源要置 `required=0`，
  否则覆盖判据会判红——「必扫的来源没有轮次」与「这个来源本来就没开」在判据里是同一件事，
  而只有前者是真问题。
- 每张图都下、都识别；失败的图如实标 `failed`，那条候选落 `pending_check`，**不是跳过**。
- 节奏不由手册定：GPU 全进程串行，谁先谁后由服务内部的优先级队列排。

**Hermes agent**（回退时）：

- Instagram → 营事编集室 csw MCP。**时间窗是唯一入口**：`csw_posts_search` 填 `start`/`end`/`order=latest`/`limit`（100 起，不够翻页取完），不要按 `account` 逐个搜、不要凭记忆猜账号名——猜出来的「零结果」只说明这个账号不在后台，不说明该品牌当天没发，**这种零结果不得记为已扫来源**。需要了解某条的来源背景时再用 `csw_accounts_list`。
- 小红书 → `opencli xiaohongshu`（search / note / download），每步随机间隔：搜索后 8–25 秒、读笔记后 5–18 秒、下载后 5–18 秒、切换平台约 45–55 秒。区间写法：`sleep $((RANDOM % (上限-下限+1) + 下限))`。
- 网页 → 优先 opencli 站点适配器（`opencli list`），没有则 WebFetch；opencli 失败先按 `opencli-autofix` 自修复重试。

#### 作业内容（引擎下发）

引擎自动派工，派工单含当期窗口与采集要求。窗口按生产约定：周一覆盖最近 72 小时，周二至周五覆盖最近 24 小时，截止 07:00。**窗口以首次进入来源库的时间为准**，不是以平台的发布时间——同一条贴文晚几天才被抓到，它属于被抓到的那一期。

### 这一阶段的底线
- **窗口内每条图文贴文都判，不设 top K、不抽样。** 只取图文：类型是图或轮播，且媒体里一个视频都没有；夹了视频的轮播不算。
- **每张图都识别。** 没真正读到实图的候选落「待核」，**不算判过，也不因此淘汰**，补齐图后重评。
- **不打数字分、不设权重。** 结论只有四档：推荐 / 备选 / 不推荐 / 待核。
- **来源不加权。** 某个账号粉丝多、某个平台条数多，都不构成优先；判的是这一条本身。
- **点赞、评论、标签、话题是输入，不是维度。** 它们帮你理解热度，不替你下结论。

### 判断框架（Van 确认版）
核心问题：**这件事有没有足够具体的变化，值得 CSW 帮读者解释一次。** 非新品也可因有依据的设计、文化、历史或当下关联成立。**品牌知名度不是标准。**

六个维度，各判 成立 / 不成立 / 不明，**每维都要给依据**（引正文原话，或指明第几张图）。编不出依据就判「不明」，不许空着，更不许编：
- change 变化必须具体——结构或使用方式改了什么、品牌首次做了什么、原产品为什么改。「某品牌发布新品」通常不够。
- use 与真实使用有关——人怎么穿、搭、住、跑、移动；产品为什么这样设计。
- gain 有 CSW 读者能理解的价值——新的使用思路、值得了解的设计逻辑、文化背景。
- compare 最好有比较参照——与上一代、品牌以往做法或同类产品的不同。参照要准确，**不虚构旧款问题**。
- explain 能产生有事实支持的编辑判断——能解释某设计影响什么使用动作。只有「好看」「有趣」不够。
- csw 视角——是否符合 CSW 的报道角度与读者。

**三句话必须答得出**：发生了什么变化？为什么值得户外用户知道？它和以前有什么不一样？答不清就写明是缺资料、角度未成立还是价值不足。

七类优先关注（老产品结构性改款；装备解决具体使用问题；品牌新的空间、社群或服务方式；装备进入新生活场景且有超出造型挪用的信息；小众品类值得解释的新设计；有真实争议或取舍的产品；能从产品解释有证据的消费或生活方式变化）与七类降低优先级（只有新配色或普通 logo 联名；换材质说不出差异；宣称创新无可核实变化；纯明星带货；缺可靠来源先补证；只能说好看；必须强行拔高成趋势）**都是倾向，不是黑名单**。

### 对照材料：五类缺一不判
判每一条之前，先备齐五类对照材料。任何一类取不到，就不要下结论，把这条落「待核」并写明缺哪一类：
1. 正式已发布的条目（`GET /api/v1/ledger/posts?since=90d&brand=品牌`）
2. 知识库范例
3. 生成过文章的贴文
4. 03 阶段的历史决定与原话（`GET /api/v1/ledger/decisions?since=90d`）
5. 上一轮台账

**30 天查重针对同一事实或同一角度，不按品牌名机械去重。** 同一品牌另一件事、同一件事另一个角度，都照常判。03 里被否决过的同事实同角度可以排除，但要写明依据，且能被人捞回来。

### 要上报的三样
1. **候选条目** `PUT /runs/{run_id}/items`：条目键 = 品牌英文或拼音小写 + 短横 + 原文链接 sha256 前 6 位（如 hxo-3fa91c，生成后不再改）。每条写 discovered_via、fetched_at、evidence_url、dedup_note、origin（dispatch / van_link / supplement）、first_seen_at。
2. **采集轮** `PUT /runs/{run_id}/sweeps`：每个采集器一条，tool 填 `csw_api`（直接调接口，不经 MCP）。found（接口返回，含重复）、fetched_unique（去重后）、reviewed（真读过正文或看过图并形成判断的）、unreviewed（只加载未展开的）、in_window、registered、result。**每条都判意味着 unreviewed 必须是 0**；不是 0 就说明这一步没跑完，如实写，不要凑。
3. **判断台账** `PUT /runs/{run_id}/intake-judgements`：窗口内每条候选一行，含四档结论、六维（各带依据）、三句话、对照结论、热度说明、gaps、image_seen。昨天已判、今天仍在窗口内的写 carried=true，**出现在台账里但不重判**。

### 先交首批
凑够一批推荐（一般 4–8 条）就先提交，等主编校准，再把其余判完的以**补件**追加，不重新提交整包。补件必须挂在已通过的交付物上。

### 交付物
文件夹 = index.md（按四档分组的逐条台账 + 采集轮次表 + 对照结论）+ images/（每条一张预览）+ trace/（sweeps.jsonl、items.jsonl、judgements.jsonl，字段与接口同名）。

#### 提交前自检

- [ ] 先调 `GET /runs/{run_id}/intake-check`，八条判据没有红的再提交。判红就修，不要带着红交上去让主编替你发现。
- [ ] **窗口内每条图文贴文都判了**：台账行数不少于采集轮上报的去重候选数，unreviewed 为 0。没判完就别说判完了。
- [ ] **每张图都识别了**；没读到实图的都落了「待核」，没有因此被淘汰。
- [ ] 六个维度齐全，**每维都有依据**，依据引的是正文原话或某张图，没有一条是编的。编不出来的判了「不明」。
- [ ] 三句话每条都答得出；答不清的写明是缺资料、角度未成立还是价值不足。
- [ ] 五类对照材料齐备；缺任何一类的条目落了「待核」并写明缺哪一类。
- [ ] 查重针对的是同一事实或同一角度，不是同一品牌名；同一品牌的另一件事没有被误杀。
- [ ] 没有给任何条目打数字分，没有按来源或粉丝数加权。
- [ ] 采集轮 tool 填的是 csw_api，found / fetched_unique / reviewed / unreviewed / in_window / registered 各有数且对得上。
- [ ] 每条条目都填了 published_at 与 first_seen_at；拿不到确切披露日期的落「待核」并写明缺的就是日期。
- [ ] 首批已成形就交了，没有为个别对象无限深挖；其余判完的走补件追加。
- [ ] 交付物结构完整：index.md 按四档分组，预览图在 images/，三份 jsonl 在 trace/。

### 05-配图与素材核

| 责任 | 上游（依赖） | 下游 | 派工 | 闸 | 动作 | 时限 | 产出类型 |
|---|---|---|---|---|---|---|---|

#### 作业内容（引擎下发）

选题批准后引擎自动派工。本任务对应一个 Van 已批准可写的条目（条目级：每条一个配图任务），只为这一条补齐最终配图和写作所需的关键事实。

每则资讯提供 3 张最终配图，对应正文三个图位：图1 最有点击力（标题下）、图2 核心信息（第二段前）、图3 细节或使用场景（第三段前）。优先资讯核心原图，其次使用场景图，再次细节图；避免重复角度与构图。

每张注明：归属条目、图位、原图来源链接、使用依据（官方发布 / 媒体转载 / 社区原帖）。使用依据不清的单独标出，交主编判断是否需要专项检查。

文案反馈缺某项事实时，定点补证并附来源；补不到就写明已查范围。一个来源失败就换已授权的其他来源，不停整期。

工具同 01-情报逐条：csw MCP、opencli（按规定插入随机间隔）、WebFetch。

交付物：文件夹 = index.md（按条目列配图清单：图位、来源链接、使用依据；补证事实与来源）+ images/（按「条目-图位」命名）。

#### 提交前自检

- [ ] 只处理了本任务对应的条目；3 张图对应三个图位。
- [ ] 图片清晰、与条目相符，角度不重复。
- [ ] 每张都写明来源链接与使用依据；依据不清的已单独标出。
- [ ] 补证事实附来源；补不到的写明已查范围。
- [ ] 文件按「条目-图位」命名，相对链接可用。

## 提交、返工与失败

- 收到派工先接单；按作业内容干活，打包 zip 一步式提交（服务端命名、版本 +1）；0 闸阶段提交即通过，有闸阶段引擎会 @审核人。
- 被退回：从任务详情的 `latest_review` 读方向与位置，改后重交；原版留底。
- 上游补件到达时任务会标「补件待返工」：先读补件再动手，交新版本即清除。
- 做不了就报告失败并写原因；平台写阶段收到「待授权」就停手报主编。
- 群消息由引擎发送；只有通知组件故障时，才按 csw-task skill §5.2 人工补发。
