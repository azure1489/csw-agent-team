3. 总体架构

代码管采集与记录，模型按 Van 的框架逐条判断并写依据，引擎仍是唯一真相。

工作 性质 用什么
取数、只取图文、下载、去重、合并、判窗口、计数、登记、结转、交付物生成 确定性 采集服务代码（Rust）
图片识别（每张图 × 该条正文） 视觉理解 视觉模型（经 sub2api）
六维初评、依据核对、同一事件、对照结论、昨日已判 窄判断、要概率 Jev（TypeSafe）
逐条综合判断：结论档、逐维判定与依据、三句话、对照解释 批量的单步判断 生成模型（经 sub2api；直连 Responses 接口或 app-server 线程，M0 对照后定）
推荐与待核条目的深核 多步、带工具、看完整图、可打断 Codex App Server（子进程）
向量化与重排 多模态检索 Qwen3-VL Embedding / Reranker（agent 主机 :8022）
知识库索引、候选、判断台账副本、图片 本机存储 LanceDB（嵌入式）+ 本地文件
任务、条目、采集轮、判断台账、交付物、闸、授权、刊发记录、决定、记忆 真相 引擎（Go + SQLite，不动）

三条边界：

  • 与引擎：采集服务只经运行面 HTTP（bearer token）读 my-tasks、tasks/:id、ledger、memory，写 items、sweeps、intake-judgements、deliverables、fail。工作台登录复用引擎的 JWT 密钥（HS256），不自己发号。
  • 与 csw-agent：只读，一把收集员 API key；不写 csw 库；补录账号仍由人在 csw 后台做。
  • 与模型：识别与判断走 sub2api；深核走 codex 子进程，sandbox=read-only、approvalPolicy=never、只读 MCP 白名单；写引擎的动作只有采集服务代码能做。

唤醒不依赖飞书 @：采集服务每 30 秒查一次 my-tasks。群播报仍由引擎单写。

4.1 十步

步 谁 做什么 产出 失败时

1 开工 采集服务 任务驱动：30 秒轮询 my-tasks，发现 open 任务即 ack、心跳，从 GET /tasks/:id 读作业标准原样注入。手动：直接开工，作业标准取当前定义 已接单 / 本地开工记录 ack 失败重试；超时由引擎升级中枢
2 采集媒体信息 采集服务 → 来源 · OSS · 视觉模型 · 向量服务 一步四段，每条候选连着做完才算采集完成：a 按 stage_code 跑采集方案，采集器直接调来源接口，只取图文，归一成统一候选格式（含点赞、评论、粉丝、csw 标签、话题），按（来源，id）去重；b 下载全部图片（w_768 缩略，05 / 11 取原图），按哈希存本地；c 每张图连同该条正文送视觉模型，出「对应正文哪一点、画面内容、正文提到但画面没有的、图片类型、可否作配图」；d 算图文融合向量与每张图的图片向量入 LanceDB 候选表 完整候选 + 每个采集器一条采集轮（found / in_window 由代码算） 必扫采集器重试三次仍失败：本步标失败、停在这里告警，不用旧接口兜底；非必扫失败记采集轮继续。单张下载或识别失败重试一次，仍失败标「未识别」，不算看过，不阻塞
3 合并与窗口 采集服务（代码为主，Jev 辅助） 窗口按「首次入库时间在上次运行之后」判定，发布时间只作 3 天时效上限；上一轮已判的标「已判」。同账号、同文案开头先粗并；候选对由品牌、时间、向量相似预筛后由 Jev 判「同一事件」；跨账号按品牌产品实体加时间近邻合并 events；事件 ↔ 候选映射 模型判定失败按粗并结果继续，标「未经模型判定」
4 对照材料 采集服务 → LanceDB · 引擎 · csw 后台 给每条候选备齐五类材料（第 6 节），缺一样不进第 5 步，标「对照材料缺」并告警。向量 + jieba 全文召回几十条，Qwen3-VL 重排到 8 条以内；候选与每条旧文的对照结论先由 Jev 三选一 每条候选一份对照材料 知识库或挑选记录读不到：本步标失败并告警，不跳过
5 逐条判断 Jev + 生成模型 每条都判，三小步：a Jev 初评（六维三档概率、类型、「值得解释」概率）；b 生成模型综合判断（输入正文与译文、每张图的描述与实图缩略、五类对照材料、作业标准、Jev 概率；要么同意要么在依据里说明分歧）；c Jev 核对每条依据是否支持该维度成立。输出见第 7 节。每批若干候选、每批新会话、并行 判断台账：每条候选一行 某批失败只重跑该批；仍失败的标「未判」并计数，不算判过

5.1 三个概念

  • 采集器：一种取法（怎么访问一个来源、怎么翻页、返回什么）。

5.5 下载与识别

每条候选的全部图片下到本地：w_768 缩略，05 / 11 取原图；按哈希存、去重。每张图连同该条正文送视觉模型，结构化输出：对应正文哪一点、画面里的产品 / 场景 / 文字、正文提到但画面没有的、图片类型（产品图 / 细节图 / 使用场景 / 海报或文字图 / 人物穿搭 / 截图 / 无关）、可否作配图。描述存 media_descriptions（候选 id、图片哈希、描述、模型与提示词版本），候选卡上每张图下一行描述。一条候选只有图片全部处理完（成功或标「未识别」）才算采集完成。app-server 不接受远程图片地址，所以深核也用本地图片。

5.6 向量化

每条候选一条图文融合向量（正文 + 代表图）、每张图一条图片向量，识别完即算、存 LanceDB 候选表。四个用处：第 4 步用它当查询检索参考库；第 3 步跨账号合并同一件事（零售商转发同一张产品图）；次日判「昨日已判」；Van 一旦在这条上做了决定，它就地变成 03 决定类参考。工作日约 1,200 个向量、9 分钟，GPU 串行、放识别之后。历史贴文池不回填：跨期转载由深核用 csw 后台自己的搜索查近 30 天；实测漏判多再按需加。

5.7 自定义三层（都不改主流程）

  1. 改方案：在工作台「运行与设置」里增删采集器、调顺序、改参数、标必扫或停用；每次改动存版本、记谁改的、从哪一期生效；可用历史窗口回放验证。覆盖「加一个账号」「多扫一个网站」「某来源暂停」。第一期建议只做这一层。
  2. 加适配器：写一个外部命令或 HTTP 端点，遵守同一份输入输出契约（输入：任务、窗口、参数；输出：统一候选格式清单、计数、错误），在方案里以「自定义采集器」登记路径或地址。沿用引擎数据子系统的外部命令方式。
  3. 挂 MCP 工具：指定 MCP 服务器与工具名，加一段字段映射，采集服务以 MCP 客户端身份直接调工具、不经模型。

5.8 统一候选格式与叠加规则

每个采集器都得给到：来源平台、来源键、外部 id、链接、账号、账号粉丝数、正文原文与语言、发布时间、抓取时间、点赞数、评论数、csw 标签、话题、媒体清单（类型、地址、哈希）、原始返回。缺发布时间或媒体的照收，但标出来。

多个采集器同时跑，结果按（来源平台，外部 id）去重；同一候选被几个采集器找到就记几条 discovered_via；来源之间不加权、不设配额。必扫采集器失败让本步标失败并告警，非必扫的只记采集轮继续。

7. 判断框架与逐条判断

7.1 Van 的框架（9/19 确认版）

核心判断：这件事有没有足够具体的变化，值得 CSW 帮读者解释一次。不能满足于汇总「户外圈发生了什么」；非新品也可因有依据的设计、文化、历史或当下关联形成报道价值。

维度 键 写稿前应识别的内容
变化必须具体 change 结构或使用方式改了什么、品牌首次做了什么、原产品为什么改、某种户外行为有什么新做法；「某品牌发布新品」通常不够
与真实使用有关 use 人怎么穿、搭、住、跑、移动，怎样在城市与户外之间切换；产品为什么这样设计。纯配色、普通 logo 联名、没有新信息的复刻通常优先级低
有 CSW 读者能理解的价值 gain 新的使用思路、值得了解的设计逻辑、文化背景、户外生活变化的解释，或帮助理解某类产品
最好有比较参照 compare 与上一代、品牌以往做法或同类产品有什么不同、为什么现在出现；参照要准确，不虚构旧款问题
能产生有事实支持的编辑判断 explain 能解释某个设计影响什么使用动作、改款对应什么需求；只有「好看」「有趣」通常还不成熟
CSW 视角（调性适配） csw 是否符合 CSW 的报道角度与读者

「具体变化 × 使用关联 × 信息增量 × 可解释性 × CSW 视角」只用于比较、排序、解释，不做机械乘法，没有一票否决。品牌知名度不是首要标准，不作维度。七类优先关注（老产品结构性改款；装备解决具体使用问题；品牌新的空间、社群或服务方式；装备进入新生活场景且有超出造型挪用的信息；小众品类值得解释的新设计；有真实争议或取舍的产品；能从产品解释有证据的消费或生活方式变化）与七类降低优先级（只有新配色或普通 logo 联名；换材质说不出差异；宣称创新无可核实变化；纯明星带货；缺可靠来源先补证；只能说好看；必须强行拔高成趋势）是倾向，不是黑名单。成稿前三句话：发生了什么变化？为什么值得户外用户知道？它和以前有什么不一样？答不清先不写，查明是缺资料、角度未成立还是价值不足。

她纠正过的五处，全部已落进本方案：初筛要看代表性实图；「不是新品的不报」不是她的意思；30 天查重针对同一事实或角度；知识库区分发布状态；证据或图片不足先待核、补齐后重评。

7.5 排序与「不打分」

排序由代码算：先按档，再按成立的维度数，再按相对账号基线的热度，最后按发布时间；只用于台账顺序。不打数字分、不设权重、没有综合分，理由：

打分本来想解决什么 现在怎么解决
几百条候选要有个顺序 每条都判，四档就是顺序；档内按成立维度数排
判断要可核 逐维「成立 / 不成立 / 不明」加一句依据，比一个 0.73 更好核；依据指向正文或某张图
准则要能调、能回测 调的是维度定义、锚点和案例；回测看她的采用 / 否决落在哪一档
不因口味淘汰 不推荐档照样保留、可捞回

加权求和恰恰是她说的机械乘法；模型给的分本身不稳定，权重一改全表重排，是假精度；综合分让人只看头部，与「每条都判」相反。以后真要精细排序，再从逐维结论按代码派生可解释的分。

7.6 热度与标签

点赞、评论、标签、话题是输入信号，模型要在依据里引用，代码用相对热度做档内排序。近一周点赞中位 76、平均 172、p90 433、最高 6,416，评论中位 0；账号之间近 90 天中位点赞从 0 到 3,113（p50 约 72），所以热度按账号自身基线归一，小账号的好东西点赞天然少、不用它否决。csw 标签里的营业时间、选品、举办日、报名日给降低提示，新品、事件、装备给优先提示，只是提示。

7.7 锚点与回测

8. Jev 窄判断：初评、核对与七处替代脆弱解析

Jev（TypeSafe System One，jev-1.13.0）返回带概率的类型化答案（三档 Score、Choice、Noul），快、便宜、稳定，但只读文字、不写字、不看对照材料。两次实测：9/20 用 477 条（148 秒、0.028 美元）时 Van 亲选排第 258、否决的排第 13 与 19；9/21 用 13 个真实事件按六维三档打（12.9 秒、3.2 万 token、0.0013 美元）：补货一条稳稳判低，类型分类全部合理，「使用关联」「调性适配」区分度高，但 Van 采用的 gnuhr「值得」只有 0.48，她否决的两条联名反而 0.60 与 0.75。结论：做初评、核对与窄判断，不做结论档。

9. 深核：Codex App Server

  • 定位：官方定位是产品内深度集成，自动化建议用 SDK；本方案只让它做深核与将来的对话入口。
  • 线程口径：每个推荐或待核候选一个线程，默认并行 3；首批限 4–8 条、10 分钟时间盒；developerInstructions 注入阶段标准、判断框架、该事件的判断结果与缺口；图片先下到线程 cwd，回合输入用 localImage；回合级超时由采集服务管，超时即 turn/interrupt，重试一次再失败向引擎报失败。
  • 进程与配置：采集服务以子进程拉起 codex app-server（stdio），独立 CODEX_HOME=/opt/csw-collector/codex-home（个人目录每回合多背约 2 万 token 底座上下文）；model_provider 指向 sub2api（wire_api = "responses"）；web_search 关闭；MCP 只挂 csw 只读白名单 9 个工具与本地 csw_kb MCP。完整配置见开发版 §7.3。
  • 最大的坑：approvalPolicy: "never" 会把需要审批的 MCP 工具调用直接拒绝。正确组合：线程级 never + sandbox: "read-only"；MCP 服务上 default_tools_approval_mode = "approve" + enabled_tools 白名单；客户端仍实现三个审批处理器并一律回 decline。
  • 过程可核：每条 item/completed 原样落盘，随交付物归档到 trace/；thread/tokenUsage/updated 按 run 汇总；分页历史模式不能创建线程，不用它做审计。
  • 硬要求：读循环不阻塞；只用 stdio、固定版本；gpt-6-astra 要求较新的 codex（0.149.0 被拒）；Linux 沙箱依赖 bwrap，agent 主机已装、M0 实测；协议与客户端直接 path 依赖 codex 仓库的 app-server-protocol / app-server-client / app-server-transport crate（锁定提交），MCP 用 rmcp 3.2。
