2.2 采集媒体信息：采集器、下载与识别是一个整体，可自定义

三个概念：采集器是一种取法（怎么访问一个来源、怎么翻页、返回什么）；来源是采集器的一个实例，参数在来源台账里（账号、地址、必扫、启停）；采集方案是按任务类型编的一份有序清单，写明跑哪些采集器、各带什么参数、哪些必扫。跑完把结果归一成同一种候选格式再合并，然后不分来源地对每条候选下载媒体、逐个识别，所以后面的合并、查重、打分不关心候选是从哪来的，也不用再碰原站。

只取图文。Reel 与含视频的轮播在采集器里就过滤掉，只有图片的 Image 与 Carousel 才进候选。近一周贴文库的实际量如下（在册账号，按入库日，UTC）：

只有图片的贴文占八成，平均每条约 5.5 张图：单图占四分之一，十张以上占一成半（Instagram 轮播上限 20 张）。一次「前一天到当天」的窗口约 380 条贴文，取图文后约 300 条、1,700 张图；因为两天窗口有一天重叠，扣掉上一轮已判过的，每天新判的量是工作日约 120 到 180 条、650 到 1,000 张图，周末减半。按并行 10 路、每张 4 秒粗估，识别一天的新图约 5 到 7 分钟；准确的速度与费用在 M0 实测。

下载与识别是这一步的一部分，不是后面的步。每条候选的全部图片都下到本地：取 w_768 缩略，05 / 11 取原图。然后每张图连同该条正文送视觉模型，结构化输出：对应正文哪一点、画面里的产品 / 场景 / 文字、正文提到但画面没有的、图片类型（产品图 / 海报 / 场景 / 截图 / 无关）、可否作配图。描述随候选保存，候选卡上每张图下一行描述。下载或识别失败的图标「未识别」，不算看过，不阻塞其他候选；一条候选只有图片全部处理完（成功或标记）才算采集完成。加新采集器不用管下载与识别，它们对所有来源通用。

自定义有三层，都不改主流程：

  1. 改方案：在工作台「运行与设置」里增删采集器、调顺序、改参数、标必扫或停用；每次改动存一个版本，记谁改的、从哪一期生效；可用历史窗口回放验证。这一层覆盖「加一个 Instagram 账号」「多扫一个网站」「某来源暂停」。
  2. 加适配器：新取法不用改采集服务代码。写一个外部命令或一个 HTTP 端点，遵守同一份输入输出契约（输入：任务、窗口、参数；输出：统一候选格式的清单、计数、错误），在方案里以「自定义采集器」登记路径或地址即可。引擎的数据子系统已经用同样的外部命令方式接平台读取，沿用它。
  3. 挂 MCP 工具：指定 MCP 服务器与工具名，加一段字段映射（哪个字段是 id、链接、正文、时间、媒体），采集服务以 MCP 客户端身份直接调工具、不经模型。适合来源方已经给了 MCP 的情形。

叠加的规则：多个采集器同时跑，结果按（来源平台，外部 id）去重；同一候选被几个采集器找到就记几条 discovered_via，来源之间不加权、不设配额。必扫采集器失败让本步标失败并告警，非必扫的失败只记采集轮继续。

统一候选格式（每个采集器都得给到这些字段）：来源平台、来源键、外部 id、链接、账号、正文原文与语言、发布时间、抓取时间、媒体清单（类型、地址、哈希）、原始返回。缺发布时间或媒体的照收，但标出来。

2.3 两种开工方式：任务驱动与手动开启

同一条流程，两个入口。任务驱动是日常：引擎派什么就做什么，结果写回引擎。手动开启是人要用这套流程做点别的：回放、验证、试新来源、临时补采；不关联任务时只在本地，关联了就和任务驱动一样交付。

项目任务驱动手动开启
谁发起引擎定时触发，或主编在管理后台触发主编、研究员、开发在工作台点「开始一轮」
参数来自任务：stage_code、run 的窗口、作业标准与自检人选：任务类型或采集方案、窗口、采集器参数、是否关联某个已接单的任务
走哪几步1 到 9 全走2 到 6 全走；7 到 9 只在关联任务时走
写不写引擎写：条目、采集轮、打分台账、交付物不关联：不写，只有本地台账与报告。关联：与任务驱动相同，以补件或产出提交
群播报引擎单写无；关联任务并提交后由引擎照旧播报
典型用途每天 05:30 那一期；05 / 11 逐条任务并行验证期只出报告不写引擎；回放历史窗口调权重与准则；试新采集器或新来源；白天临时补采 Van 给的链接；某一步失败后只重跑那一步
审计引擎的任务事件发起人、参数、时间写审计；本地台账标「手动」，与任务驱动的轮次分开列
与任务的关系一轮对一个任务可以不关联；也可以先跑后关联，把挑出的结果以补件挂到任务上

2.4 每条都判：判断的输入与输出

窗口内每一条图文贴文都要判一遍，每一张图都要识别一遍，不再只看排名靠前的。判断不是模型凭正文自由发挥，而是拿着三样对照材料做综合判断，缺一样就不判、标「对照材料缺」并告警。

2.5 打分规则还要不要

之前的设计是六个维度各打分、按权重加成综合分、按综合分排序，权重版本可调可回测。对照 Van 的反馈和现在的要求，我的分析是：维度要留，数字分和权重不要。

打分本来想解决什么现在怎么解决
几百条候选要有个顺序每条都判，结论档四档就是顺序；档内按成立的维度数排，够用
判断要可核逐维「成立 / 不成立 / 不明」加一句依据，比一个 0.73 更好核；依据指向正文或某张图
准则要能调、能回测调的是维度定义、锚点和案例，不是权重；回测看她的采用 / 否决落在哪一档（命中率），不需要数字
不因口味淘汰不推荐档照样保留、可捞回，与打分无关

数字分的坏处也具体：Van 说过维度不是机械乘法、没有一票否决，加权求和恰恰是机械乘法；模型给的 0 到 1 的分本身不稳定，同一条重跑会漂，权重一改全表重排，看起来严谨其实是假精度；主编和研究员看综合分容易只看头部，和「每条都判」的初衷相反。如果以后真要精细排序，再从逐维结论按代码派生一个可解释的分（成立维度数），不让模型报数。

结论：第 5 步输出结论档 + 逐维依据 + 三句话 + 对照结论，不设权重版本；判断框架页保留维度定义、锚点与案例的版本和回测，删掉权重表。请在第 7 节第 2 条确认。

1 接单 / 手动开工工作台（采集服务）任务驱动：每 30 秒查 my-tasks，发现 open 的任务即 ack 并开始心跳，从 GET /tasks/:id 读作业内容、自检、验收，原样显示并注入后面的判断前言。手动开启：直接开工，作业标准取当前定义里对应阶段的版本（只读，不算接单）；两种方式之后走同一条线。任务状态：已接单；或本地开工记录流程带全部步置「待开始」；作业标准可读；开工方式标明。主编可「中止本轮」或「重新开始」（记录人与理由）。ack 失败重试；超过 ack 时限由引擎升级中枢，照旧。
2 采集媒体信息工作台 → 来源 · OSS · 模型一步三段，对每条候选连着做完才算采集完成，不分来源。a 取候选：读任务 stage_code 选采集方案，方案里的采集器逐个跑一轮（csw 贴文窗口 GET /api/v1/posts/window；单条 GET /api/v1/posts/{id}?include-media=true；小红书 opencli 受控调用；网页按域名白名单抓取；Van 链接按 id 取单条），只取图文：Reel 与含视频的轮播不取，只有图片的 Image / Carousel 取；结果归一成统一候选格式，按（来源，id）去重，记 discovered_via。b 下载图片：每条候选的全部图片，取 w_768 缩略（05 / 11 取原图），按哈希存本地，失败记原因。c 识别：每张图连同该条正文送视觉模型，结构化输出对应正文哪一点、画面里的产品 / 场景 / 文字、正文提到但画面没有的、图片类型（产品图 / 海报 / 场景 / 截图 / 无关）、可否作配图；存 media_descriptions（候选 id、图片哈希、描述、模型与提示词版本）。全部直接调接口，不经 csw MCP。完整候选：正文 + 本地图片 + 每张图一条描述与用途判断；每个采集器一条采集轮（found / in_window 由代码算）跑了哪些采集器、各自数量与耗时；过滤掉的视频贴文数；下载成功率与读不到的清单；识别进度与未识别的；候选卡上每张图下一行描述。改采集方案（增删采集器、排序、参数、启停，写审计）；改窗口重取；对某张图重下、重识别或手改描述（留痕）。必扫采集器重试三次仍失败：本步标失败、停在这里告警；非必扫失败记采集轮 failed 继续。单张下载或识别失败重试一次，仍失败标「未识别」，不算看过，不阻塞。不用旧接口兜底。
3 合并与窗口工作台（代码为主）窗口按「首次入库时间在上次运行之后」判定（接口的 ingestedAt），发布时间只作时效上限（默认 3 天内），这样 01:00 之后才发、次日才入库的贴文不会被当成窗口外；上一轮已判过的候选标「已判」，不重复提报。同账号、同文案开头先粗并；模型判是否同一事件（可选）；跨账号同一件事按识别出的品牌、产品实体加时间近邻合并。events 表；事件 ↔ 候选映射新入库数、事件数、每个事件合并了哪几条、窗口外与已判分组。拆开或合并事件（留痕）。模型判定失败时按粗并结果继续，标「未经模型判定」。
4 对照材料工作台（代码检索）→ 引擎 · csw 后台给每条候选备齐三样材料，缺一样就不进第 5 步，标「对照材料缺」并告警。一，知识库：按品牌、产品、别名检索正式已发布的文章与十篇范例，附发布日期与角度；知识库同步到哪一天写进材料。二，已挑选记录：csw 后台里 Van 勾选过的贴文（selections 接口）与生成过文章的贴文（posts/generated 接口）、引擎里历次 03 决定（采用 / 否决 / 暂缓，附原话）、上一轮判断台账里的同品牌条目。三，判断框架：Van 的核心问题「这件事有没有足够具体的变化，值得 CSW 帮读者解释一次」、六个维度与锚点、三句话、优先 / 降低七类、相关案例原话。每条候选一份对照材料：旧文命中、已选 / 已否记录、相似案例、框架与锚点每条候选的对照材料可展开；知识库与挑选记录的同步时间。补一条旧文或案例（留痕）。知识库或挑选记录读不到：本步标失败并告警，不跳过。
5 逐条综合判断工作台 → 模型每条候选都判一遍，不设 top K。输入：正文与译文、每张图的描述与实图缩略、第 4 步的三样对照材料、任务下发的作业标准。输出：结论档（推荐 / 备选 / 不推荐 / 待核）；六个维度逐项「成立 / 不成立 / 不明」各配一句依据；三句话试答；与已发、已选的对照结论（同一事实无新增 / 同品牌有新增 / 不相干，附对照对象）；缺口；是否看到实图。不给数字分、不设权重，排序由代码按「档 → 成立的维度数 → 发布时间」算（见 2.5 的分析）。每批若干候选、每批新会话、并行。判断台账：每条候选一行台账全量；按档分组；逐维依据与三句话；缺口；对照对象可点开。改档、补依据、标待核、加入首批（都留痕）。某批失败只重跑该批；重试后仍失败的候选标「未判」并计数，不算判过。
6 深核工作台 → Codex App Server推荐档与待核档各起一个线程：核原始披露时间、找原始来源核事实、核比较参照是否准确、看完整图片；工具只挂只读白名单；线程事件流落盘。首批只做前 4 到 8 条并限 10 分钟，超时的按待核交，其余以补件追加。条目卡：披露时间、证据链接、对照说明、事实、配图、缺口详情页深核结果与证据；线程记录可下载；进度。打断某个线程、改条数、对单个候选重跑。单线程超时或失败标「深核未完成」，条目仍可登记并写明缺口。
7 登记与交付工作台 → 引擎只在本轮关联了任务时做：PUT items（带 origin）、PUT sweeps、PUT intake-judgements（判断台账，引擎需新增）；生成 index.md + images/ + trace/ 打 zip；提交前本地跑 intake-check；submit（kind=产出；关联到已通过任务的用 kind=补件）。推荐档与待核档登记为条目；其余每条也进引擎的判断台账，intake-check 的「产出落差」判据改读台账。手动开启且未关联任务：不写引擎、不群播报，只出本地台账与报告，事后可挑选结果关联到某个任务以补件提交。关联任务：引擎里的条目、采集轮、判断台账、交付物，任务状态待审。未关联：本地报告校验结果逐条、提交状态、交付物链接；未关联时显示「本地」并给「关联到任务」入口。主编可在提交前先看一眼台账并调整首批（可选，不改闸的位置）；把手动轮的结果关联到任务。intake-check 不过则不提交，列出不过项；submit 失败重试，幂等键固定。
8 首批校准引擎闸 · 主编引擎群播报「待审」；主编在工作台看台账、图与描述、缺口，回引擎「通过」或「退回」（退回必填方向与位置）。任务：已交付 / 需返工闸状态、退回原因。通过、退回、定点意见。超时由引擎照旧提醒。
9 返工或补件工作台 → 引擎退回：按 latest_review 的方向与位置返工，重新交付。通过：其余候选与后续补证以 kind=补件 追加到已通过任务，每期合并成一次补件，除非主编要求；只让已开工的直接下游返工。补件记录补件清单与状态。主编触发「追加补件」。同 7。

5 与 9/20 设计稿的差异

  1. 起点写清楚了：0 派单 → 1 接单，之前的设计图从「取全量」起画，看不出接单在前。
  2. 开工有两种方式：任务驱动与手动开启，之后走同一条线；手动开启不关联任务时只出本地台账与报告，不写引擎、不群播报，用于回放历史窗口、并行验证、试新采集器或来源、白天临时补采；关联任务时与任务驱动一样登记交付。
  3. 只取图文：Reel 与含视频的轮播不取。近一周在册账号每天入库 103 到 223 条，其中只有图片的占八成，每条平均约 5 张图；一次「前一天到当天」的窗口约 380 条、图文 300 条、1,700 张图，去掉上一轮已判的后每天新判约 120 到 180 条、650 到 1,000 张图（见 2.2 的估算表）。
  4. 第 2 步从「取全量」改为「采集媒体信息」：取候选、下载图片、识别合成一个整体，每条候选出这一步时已带本地图片与每张图的描述和用途判断；之前下缩略图和看图分散在 B、D 两步。
  5. 第 2 步按任务类型跑一套可配置的采集方案，采集器直接调来源接口、不经 csw MCP；取 csw-agent 贴文只是其中一个采集器，以后加来源是改清单、加取法是加采集器；MCP 只留给深核线程按需查。
  6. 贴文库抓取从每天 05:00 改到 01:00（9/21 已改生产，配置在 instagram-data）；窗口判定改按首次入库时间，发布时间只作时效上限，堵住凌晨到早上这段的漏洞。
  7. 第 4 步「对照材料」三样必备：知识库、已挑选记录（csw 后台 Van 的挑选、引擎 03 决定、上一轮台账）、Van 判断框架；缺一样不判。之前写的是「有则用」，撤回。
  8. 第 5 步从「打分」改为「逐条综合判断」：每条候选都判，不设 top K；输出结论档与逐维依据、三句话、对照结论，不给数字分、不设权重（分析见 2.5）。
  9. 整条流程做成工作台顶部的流程带，每一步可点开看产物、失败与重跑；之前总览只有一条进度条。
  10. 05 配图与素材核、11 选图包明确为同一工作台接单，同一起点，采集媒体信息走「条目取单条」方案。

6 不变的约定

  • 引擎仍是唯一真相：任务、条目、采集轮、判断台账、交付物、闸、授权都在引擎；工作台读引擎、写引擎，不另存状态。
  • 群播报仍由引擎单写；工作台不发群消息。
  • 01 的主编首批校准闸位置不变；其余候选以补件追加，不重跑已批内容。
  • Van 的决定仍经 03 闸生效；工作台上的勾选先记「Van 选择」，由主编代录并附原话。
  • 作业标准、自检、验收仍以引擎定义为准，工作台原样显示，不另抄一份。

7 请确认

  1. 只取图文的口径：严格（贴文里只要有视频就不取，约占入库量八成）还是宽松（只排除 Reel，混合轮播取其中的图片，约占八成五到九成），建议先严格。
  2. 第 5 步不打数字分、不设权重，改为结论档 + 逐维依据，排序由代码按档与成立维度数算，是否同意（分析见 2.5）。
  3. 图片描述与用途判断每张一条，存采集服务本地并随台账显示；是否同时回写 csw 库的 detailed_alt，请定。
  4. 必扫采集器失败时停在第 2 步告警、不用旧接口兜底，是否同意。
  5. 第 7 步提交前是否允许主编先在工作台调整首批再提交（可选项，不改闸的位置）。
  6. Van 模式的勾选是否直接等同 03 闸决定，还是只记「Van 选择」由主编代录（沿用设计说明第 10 节的问题）。
