# 情报收集员工作台 · 总方案

日期：2026-09-21｜发出：开发｜状态：总方案，合并《完整流程》确认稿第 16 版、《设计说明》第 4 版、《架构与部署分析》第 2 版、开发版第三版、概要版第二版与接续记录 §19–§35｜读者：Van、主编、开发

**一句话**：把情报收集员从 Hermes agent 换成一个工作台。一个 Rust 采集服务按引擎派单或人工开启，跑完「采集媒体信息 → 合并 → 对照材料 → 逐条判断 → 深核 → 登记交付」，窗口内每条图文贴文都判、每张图都识别，判断以五类参考和 Van 的框架为依据，过程全部可见、可核、可重跑；引擎仍是唯一真相。

## 1. 为什么改：现状与目标

### 1.1 现状证据（r48，9/18 期）

| 通道 | 接口返回 | 去重后 | 实际看过 | 没看过 | 登记 |
|---|---|---|---|---|---|
| Instagram（csw MCP） | 401 | 401 | **49** | **352** | 49 |
| 网页（opencli） | 123 | 70 | **0** | **70** | 0 |
| 小红书（opencli） | 37 | 37 | **1** | **36** | 1 |

- 01 任务首末事件相隔 188 分钟，交了 3 版；数字全是 agent 自报，无法核对。
- **来源不全**：这一期 Van 退回两条选题后自己发来 8 条 Instagram 链接，7 篇成稿全部出自这 8 条；按短码核对，8 条里只有 1 条在贴文库。后台在册 460 个账号，近 7 天日均入库 158 条。
- **知识库停在 9/15**：生产上没有同步定时器；公众号已出到 vol.260，引擎刊发记录只有 51 篇（15 篇有正文、拆条 6 条），反馈记忆 6 条。
- **不看图、无译文**：`translated_text` 全空，`detailed_alt` 覆盖率 0；模型只凭正文挑。
- **接口取不全**：旧接口 `posts/search` 最多返回 100 条、页码写死；「前一天到当天」实际 438 条（已用新接口 `posts/window` 解决，见第 14 节）。
- **权限面过大**：Hermes 上的收集员挂着 csw MCP 全部 25 个工具（含推公众号）和终端，读的是不可信输入。

根因：取不全；单会话装不下；判断标准没落进系统（无知识库、无偏好记忆、不看实图）；确定性工作交给了模型；来源名单与知识库不随时间更新。

### 1.2 改造目标（Van 9/19 确认版）

更早、独立地找到她愿意采用的选题，减少她补链接、反复解释和催促。

**目标指标**（数值结合实测再定）：

| 指标 | 记录口径 | 埋点 |
|---|---|---|
| 自主发现情况 | 最终采用的选题里，系统在她提供链接之前独立发现了多少 | 条目加 `origin`（system / van_link / editor_link）与 `first_seen_at` |
| 第一轮推荐质量 | 第一轮推荐多少条、采用多少条、随后补选几轮 | 03 闸首版条数、Van 首次采用数、03 版本数与退回次数（引擎已有） |
| Van 的实际投入 | 审题、补充说明、补链接所花时间 | 03 与 08 从送达到决定的用时；`van_link` 条目数；补充说明条数（估算） |

她提供链接后的处理结果单独记录，不计入自主发现。

**技术指标**：

| 指标 | 现状（r48） | 目标 |
|---|---|---|
| 审阅覆盖：窗口内图文贴文被逐条判断 | 49 / 401 | 100%，由代码计数 |
| 看图覆盖：判断时实际看到实图 | 0 | 如实统计；读不到的标待核 |
| 来源覆盖：采用条目的来源账号在册 | 1 / 8 | 逐期上升 |
| 召回（只算来源在册的部分） | 无法测 | 并行期 ≥ 90%；不单独作为成功依据 |
| 01 用时 | 188 分钟 | 首批 20 分钟、全量 45 分钟（测试目标） |
| 写权限面 | 25 个 MCP 工具加终端 | 只读工具；写引擎仅采集服务代码 |

速度与覆盖达标之外，要证明推荐更符合要求、她少补题少解释少催促，才算成功。不设「凑满 6 主 2 备」的硬指标，不拿弱题凑数。

## 3. 总体架构

<!-- FIG:system -->

**代码管采集与记录，模型按 Van 的框架逐条判断并写依据，引擎仍是唯一真相。**

| 工作 | 性质 | 用什么 |
|---|---|---|
| 取数、只取图文、下载、去重、合并、判窗口、计数、登记、结转、交付物生成 | 确定性 | 采集服务代码（Rust） |
| 图片识别（每张图 × 该条正文） | 视觉理解 | 视觉模型（经 sub2api） |
| 六维初评、依据核对、同一事件、对照结论、昨日已判 | 窄判断、要概率 | Jev（TypeSafe） |
| 逐条综合判断：结论档、逐维判定与依据、三句话、对照解释 | 批量的单步判断 | 生成模型（经 sub2api；直连 Responses 接口或 app-server 线程，M0 对照后定） |
| 推荐与待核条目的深核 | 多步、带工具、看完整图、可打断 | Codex App Server（子进程） |
| 向量化与重排 | 多模态检索 | Qwen3-VL Embedding / Reranker（agent 主机 :8022） |
| 知识库索引、候选、判断台账副本、图片 | 本机存储 | LanceDB（嵌入式）+ 本地文件 |
| 任务、条目、采集轮、判断台账、交付物、闸、授权、刊发记录、决定、记忆 | 真相 | 引擎（Go + SQLite，不动） |

**三条边界**：

- **与引擎**：采集服务只经运行面 HTTP（bearer token）读 my-tasks、tasks/:id、ledger、memory，写 items、sweeps、intake-judgements、deliverables、fail。工作台登录复用引擎的 JWT 密钥（HS256），不自己发号。
- **与 csw-agent**：只读，一把收集员 API key；不写 csw 库；补录账号仍由人在 csw 后台做。
- **与模型**：识别与判断走 sub2api；深核走 codex 子进程，`sandbox=read-only`、`approvalPolicy=never`、只读 MCP 白名单；写引擎的动作只有采集服务代码能做。

唤醒不依赖飞书 @：采集服务每 30 秒查一次 `my-tasks`。群播报仍由引擎单写。

## 4. 完整流程

<!-- FIG:full -->

### 4.1 十步

| 步 | 谁 | 做什么 | 产出 | 失败时 |
|---|---|---|---|---|
| **0 入口** | 引擎 或 人 | 贴文库 01:00 抓完（约半小时内入库）。任务驱动：引擎 05:30 触发 run（周一窗口到上周五），01 派给「情报收集员」角色，群播报由引擎单写。手动开启：主编、研究员或开发在工作台点「开始一轮」，选任务类型或采集方案、窗口、参数、是否关联已接单任务；发起人与参数写审计 | run · 任务 · 派工单；或本地开工记录 | 引擎触发失败照旧走引擎告警；手动参数不合法当场拒绝 |
| **1 开工** | 采集服务 | 任务驱动：30 秒轮询 my-tasks，发现 open 任务即 ack、心跳，从 `GET /tasks/:id` 读作业标准原样注入。手动：直接开工，作业标准取当前定义 | 已接单 / 本地开工记录 | ack 失败重试；超时由引擎升级中枢 |
| **2 采集媒体信息** | 采集服务 → 来源 · OSS · 视觉模型 · 向量服务 | 一步四段，每条候选连着做完才算采集完成：**a** 按 `stage_code` 跑采集方案，采集器直接调来源接口，只取图文，归一成统一候选格式（含点赞、评论、粉丝、csw 标签、话题），按（来源，id）去重；**b** 下载全部图片（w_768 缩略，05 / 11 取原图），按哈希存本地；**c** 每张图连同该条正文送视觉模型，出「对应正文哪一点、画面内容、正文提到但画面没有的、图片类型、可否作配图」；**d** 算图文融合向量与每张图的图片向量入 LanceDB 候选表 | 完整候选 + 每个采集器一条采集轮（found / in_window 由代码算） | 必扫采集器重试三次仍失败：本步标失败、停在这里告警，**不用旧接口兜底**；非必扫失败记采集轮继续。单张下载或识别失败重试一次，仍失败标「未识别」，不算看过，不阻塞 |
| **3 合并与窗口** | 采集服务（代码为主，Jev 辅助） | 窗口按「首次入库时间在上次运行之后」判定，发布时间只作 3 天时效上限；上一轮已判的标「已判」。同账号、同文案开头先粗并；候选对由品牌、时间、向量相似预筛后由 Jev 判「同一事件」；跨账号按品牌产品实体加时间近邻合并 | events；事件 ↔ 候选映射 | 模型判定失败按粗并结果继续，标「未经模型判定」 |
| **4 对照材料** | 采集服务 → LanceDB · 引擎 · csw 后台 | 给每条候选备齐五类材料（第 6 节），缺一样不进第 5 步，标「对照材料缺」并告警。向量 + jieba 全文召回几十条，Qwen3-VL 重排到 8 条以内；候选与每条旧文的对照结论先由 Jev 三选一 | 每条候选一份对照材料 | 知识库或挑选记录读不到：本步标失败并告警，不跳过 |
| **5 逐条判断** | Jev + 生成模型 | 每条都判，三小步：**a** Jev 初评（六维三档概率、类型、「值得解释」概率）；**b** 生成模型综合判断（输入正文与译文、每张图的描述与实图缩略、五类对照材料、作业标准、Jev 概率；要么同意要么在依据里说明分歧）；**c** Jev 核对每条依据是否支持该维度成立。输出见第 7 节。每批若干候选、每批新会话、并行 | 判断台账：每条候选一行 | 某批失败只重跑该批；仍失败的标「未判」并计数，不算判过 |
| **6 深核** | Codex App Server | 推荐档与待核档各起线程：核原始披露时间、找原始来源、核比较参照、看完整图；只挂只读白名单；线程事件流落盘。首批只做前 4–8 条、限 10 分钟，超时的按待核交，其余以补件追加 | 条目卡：披露时间、证据链接、对照说明、事实、配图、缺口 | 单线程超时或失败标「深核未完成」，条目仍可登记并写明缺口 |
| **7 登记与交付** | 采集服务 → 引擎 | 只在关联任务时：`PUT items`（带 origin）、`PUT sweeps`、`PUT intake-judgements`（引擎待新增）；生成 `index.md` + `images/` + `trace/` 打 zip；提交前本地跑 `intake-check`；submit（产出 / 补件）。推荐与待核登记为条目；其余每条也进判断台账。手动未关联：不写引擎，只出本地报告，事后可关联到任务以补件提交 | 引擎里的条目、采集轮、判断台账、交付物；或本地报告 | intake-check 不过则不提交并列出不过项；submit 失败重试，幂等键固定 |
| **8 首批校准** | 引擎闸 · 主编 | 引擎群播报「待审」；主编在工作台看台账、图与描述、缺口，回引擎通过或退回（方向 + 位置） | 已交付 / 需返工 | 超时由引擎照旧提醒 |
| **9 返工或补件** | 采集服务 → 引擎 | 退回：按 `latest_review` 返工重交。通过：其余候选与补证以补件追加到已通过任务，**每期合并一次**；只让已开工的直接下游返工 | 补件记录 | 同 7 |
| **下游** | 引擎 · 研究员 · 主编 · Van | 02 读判断台账与 intake-trace 评估；03 主编合成方案；Van 在工作台 Van 模式勾选并留原话，主编代录 03 决定；决定连同当时的判断结论入选题记忆，下一期第 4、5 步读得到 | 03 决定；记忆案例 | —— |
| **05 / 11** | 引擎 → 同一采集服务 | 05 配图与素材核（`material`，逐条自动派工）与 11 小红书选图包（`xhs_pick`，逐条手动派工）同样接单，走「条目取单条」：取该贴文、下原图、识别与用途判断，再核素材与版权、逐条交付（0 闸）；不走合并、对照、判断、深核 | 逐条交付物 | 同 1、2 |

### 4.2 两种开工方式

| 项目 | 任务驱动 | 手动开启 |
|---|---|---|
| 谁发起 | 引擎定时触发，或主编在管理后台触发 | 主编、研究员、开发在工作台点「开始一轮」 |
| 参数来自 | 任务：`stage_code`、run 的窗口、作业标准与自检 | 人选：任务类型或采集方案、窗口、采集器参数、是否关联某个已接单的任务 |
| 走哪几步 | 1 到 9 全走 | 2 到 6 全走；7 到 9 只在关联任务时走 |
| 写不写引擎 | 写：条目、采集轮、判断台账、交付物 | 不关联：不写。关联：与任务驱动相同，以补件或产出提交 |
| 群播报 | 引擎单写 | 无；关联并提交后由引擎照旧播报 |
| 典型用途 | 每天 05:30 那一期；05 / 11 逐条任务 | 并行验证期只出报告；回放历史窗口调准则与锚点；试新采集器或新来源；白天临时补采 Van 给的链接；某一步失败后只重跑那一步 |
| 审计 | 引擎的任务事件 | 发起人、参数、时间写审计；本地台账标「手动」，与任务驱动的轮次分开列 |

### 4.3 早上的时间表

| 时刻 | 发生什么 |
|---|---|
| 01:00 | `instagram-data` 触发 Bright Data 抓取，约 01:30 前入库（一次 170–230 条） |
| 05:30 | 引擎触发 run，01 派给收集员角色；采集服务 30 秒内接单 |

### 5.5 下载与识别

每条候选的全部图片下到本地：w_768 缩略，05 / 11 取原图；按哈希存、去重。每张图连同该条正文送视觉模型，结构化输出：对应正文哪一点、画面里的产品 / 场景 / 文字、正文提到但画面没有的、图片类型（产品图 / 细节图 / 使用场景 / 海报或文字图 / 人物穿搭 / 截图 / 无关）、可否作配图。描述存 `media_descriptions`（候选 id、图片哈希、描述、模型与提示词版本），候选卡上每张图下一行描述。一条候选只有图片全部处理完（成功或标「未识别」）才算采集完成。app-server 不接受远程图片地址，所以深核也用本地图片。

### 5.6 向量化

每条候选一条图文融合向量（正文 + 代表图）、每张图一条图片向量，识别完即算、存 LanceDB 候选表。四个用处：第 4 步用它当查询检索参考库；第 3 步跨账号合并同一件事（零售商转发同一张产品图）；次日判「昨日已判」；Van 一旦在这条上做了决定，它就地变成 03 决定类参考。工作日约 1,200 个向量、9 分钟，GPU 串行、放识别之后。历史贴文池不回填：跨期转载由深核用 csw 后台自己的搜索查近 30 天；实测漏判多再按需加。

### 5.7 自定义三层（都不改主流程）

1. **改方案**：在工作台「运行与设置」里增删采集器、调顺序、改参数、标必扫或停用；每次改动存版本、记谁改的、从哪一期生效；可用历史窗口回放验证。覆盖「加一个账号」「多扫一个网站」「某来源暂停」。**第一期建议只做这一层。**
2. **加适配器**：写一个外部命令或 HTTP 端点，遵守同一份输入输出契约（输入：任务、窗口、参数；输出：统一候选格式清单、计数、错误），在方案里以「自定义采集器」登记路径或地址。沿用引擎数据子系统的外部命令方式。
3. **挂 MCP 工具**：指定 MCP 服务器与工具名，加一段字段映射，采集服务以 MCP 客户端身份直接调工具、不经模型。

### 5.8 统一候选格式与叠加规则

每个采集器都得给到：来源平台、来源键、外部 id、链接、账号、账号粉丝数、正文原文与语言、发布时间、抓取时间、点赞数、评论数、csw 标签、话题、媒体清单（类型、地址、哈希）、原始返回。缺发布时间或媒体的照收，但标出来。

多个采集器同时跑，结果按（来源平台，外部 id）去重；同一候选被几个采集器找到就记几条 `discovered_via`；来源之间不加权、不设配额。必扫采集器失败让本步标失败并告警，非必扫的只记采集轮继续。

## 7. 判断框架与逐条判断

### 7.1 Van 的框架（9/19 确认版）

核心判断：**这件事有没有足够具体的变化，值得 CSW 帮读者解释一次。**不能满足于汇总「户外圈发生了什么」；非新品也可因有依据的设计、文化、历史或当下关联形成报道价值。

| 维度 | 键 | 写稿前应识别的内容 |
|---|---|---|
| 变化必须具体 | `change` | 结构或使用方式改了什么、品牌首次做了什么、原产品为什么改、某种户外行为有什么新做法；「某品牌发布新品」通常不够 |
| 与真实使用有关 | `use` | 人怎么穿、搭、住、跑、移动，怎样在城市与户外之间切换；产品为什么这样设计。纯配色、普通 logo 联名、没有新信息的复刻通常优先级低 |
| 有 CSW 读者能理解的价值 | `gain` | 新的使用思路、值得了解的设计逻辑、文化背景、户外生活变化的解释，或帮助理解某类产品 |
| 最好有比较参照 | `compare` | 与上一代、品牌以往做法或同类产品有什么不同、为什么现在出现；参照要准确，不虚构旧款问题 |
| 能产生有事实支持的编辑判断 | `explain` | 能解释某个设计影响什么使用动作、改款对应什么需求；只有「好看」「有趣」通常还不成熟 |
| CSW 视角（调性适配） | `csw` | 是否符合 CSW 的报道角度与读者 |

「具体变化 × 使用关联 × 信息增量 × 可解释性 × CSW 视角」只用于比较、排序、解释，不做机械乘法，没有一票否决。**品牌知名度不是首要标准**，不作维度。七类优先关注（老产品结构性改款；装备解决具体使用问题；品牌新的空间、社群或服务方式；装备进入新生活场景且有超出造型挪用的信息；小众品类值得解释的新设计；有真实争议或取舍的产品；能从产品解释有证据的消费或生活方式变化）与七类降低优先级（只有新配色或普通 logo 联名；换材质说不出差异；宣称创新无可核实变化；纯明星带货；缺可靠来源先补证；只能说好看；必须强行拔高成趋势）是倾向，不是黑名单。成稿前三句话：**发生了什么变化？为什么值得户外用户知道？它和以前有什么不一样？**答不清先不写，查明是缺资料、角度未成立还是价值不足。

她纠正过的五处，全部已落进本方案：初筛要看代表性实图；「不是新品的不报」不是她的意思；30 天查重针对同一事实或角度；知识库区分发布状态；证据或图片不足先待核、补齐后重评。

### 7.2 每条都判，三小步

**a Jev 初评**：对全部候选，六个维度各给三档概率（不成立 / 不明 / 成立）、类型、「值得解释」概率；输入正文、译文、每张图的描述、标签、相对热度。一天约 300 条、30 秒、3 美分。

**b 生成模型综合判断**：输入正文与译文、每张图的描述与实图缩略、五类对照材料（每条带类型、日期、出处、原话）、任务下发的作业标准、Jev 的六维概率；模型要么同意，要么在依据里说明分歧。每批若干候选、每批新会话、并行。

**c Jev 核对**：对每条依据问「这句话是否支持该维度成立」，抓编造的依据；不一致的标出来给人看。

### 7.5 排序与「不打分」

排序由代码算：先按档，再按成立的维度数，再按相对账号基线的热度，最后按发布时间；只用于台账顺序。不打数字分、不设权重、没有综合分，理由：

| 打分本来想解决什么 | 现在怎么解决 |
|---|---|
| 几百条候选要有个顺序 | 每条都判，四档就是顺序；档内按成立维度数排 |
| 判断要可核 | 逐维「成立 / 不成立 / 不明」加一句依据，比一个 0.73 更好核；依据指向正文或某张图 |
| 准则要能调、能回测 | 调的是维度定义、锚点和案例；回测看她的采用 / 否决落在哪一档 |
| 不因口味淘汰 | 不推荐档照样保留、可捞回 |

加权求和恰恰是她说的机械乘法；模型给的分本身不稳定，权重一改全表重排，是假精度；综合分让人只看头部，与「每条都判」相反。以后真要精细排序，再从逐维结论按代码派生可解释的分。

### 7.6 热度与标签

点赞、评论、标签、话题是输入信号，模型要在依据里引用，代码用相对热度做档内排序。近一周点赞中位 76、平均 172、p90 433、最高 6,416，评论中位 0；账号之间近 90 天中位点赞从 0 到 3,113（p50 约 72），所以热度按账号自身基线归一，小账号的好东西点赞天然少、不用它否决。csw 标签里的营业时间、选品、举办日、报名日给降低提示，新品、事件、装备给优先提示，只是提示。

### 7.7 锚点与回测

每一档的锚点引用范例条目（`docs/知识库/范例/*/范例拆解.md`）与被否案例。范例上六维几乎全「成立」（41 条里只 1 条 `use` 不明），只能给上限；阈值以 03 决定里的否决为准。界面设计稿用 13 个真实事件回测：两条被 Van 否的联名落在推荐 / 备选，说明「联名」锚点要收紧。M3 做重复判断的一致性检验。

## 8. Jev 窄判断：初评、核对与七处替代脆弱解析

Jev（TypeSafe System One，`jev-1.13.0`）返回带概率的类型化答案（三档 Score、Choice、Noul），快、便宜、稳定，但只读文字、不写字、不看对照材料。两次实测：9/20 用 477 条（148 秒、0.028 美元）时 Van 亲选排第 258、否决的排第 13 与 19；9/21 用 13 个真实事件按六维三档打（12.9 秒、3.2 万 token、0.0013 美元）：补货一条稳稳判低，类型分类全部合理，「使用关联」「调性适配」区分度高，但 Van 采用的 gnuhr「值得」只有 0.48，她否决的两条联名反而 0.60 与 0.75。**结论：做初评、核对与窄判断，不做结论档。**

| 用法 | 问什么 | 放在哪一步 |
|---|---|---|
| 六维度初评 | 六个三档 Score + 类型 Choice + 「值得解释」Noul | 第 5 步 a，全部候选；概率进生成模型输入，也是回测与校准的连续量 |
| 依据核对 | 「这句依据是否支持该维度成立」（Noul） | 第 5 步 c |
| 同一事件 | 两条候选是否同一件事（Noul），候选对预筛后逐对问 | 第 3 步 |
| 对照结论 | 同一事实无新增 / 同品牌有新增 / 不相干（Choice） | 第 4 步，生成模型只解释 |
| 昨日已判、03 否决同事实同角度 | Noul | 第 3、4 步 |

**七处替代脆弱解析**（代码先找候选，Jev 从候选里选，选出的值原样复制，不生成）：

1. **公众号文章拆条**：引擎 `ledger/split.go` 与范例脚本都靠正则与启发式；改为对每个段落块分类（条目序号 / 品牌行 / 标题行 / 正文 / 导读 / 尾部 / 图注），代码按块类型组装。
2. **发售日期、价格、规格**：正则找出全部日期与金额作候选，Jev 选哪一个是这件产品的；日期比较仍在代码。替代 intake-check 里的多格式时间解析，也给深核用。
3. **品牌与产品名**：候选来自 csw 标签、账号名、大写词、别名表，Jev 选出，喂全文查重与跨账号合并。
4. **待补录账号对账**：文章里的品牌名对候选账号，判哪一个是官方号。
5. **反馈记忆回收**：Van 每条发言分成选题决定 / 写作表达 / 其他，对象从当期候选里选，身份判案例还是长期规则；原话原样保留。
6. **退回原因归类**：退回原话归到反馈标签集。
7. **intake-check 的「淘汰交代」「查重对照」**：从查非空改为判这段文字是否真的给了理由或结论。

不用 Jev 的：依据、三句话、对照说明这类要写字的；深核这类要用工具的；看图；最终结论档。请求格式：不支持请求级 `instructions`（放进每个问题）；Choice 的选项字段是 `criteria` 对象。前提：输入发往第三方，贴文正文与图片描述可以，Van 群聊原话是否送出单独拍板。密钥在开发机 `~/.typesafe/.env`，不入库。

## 9. 深核：Codex App Server

> **9/22 已在 agent 主机实测通过（十项全过）**，详见 `docs/实测记录_codex_app_server部署_20260922.md`。装的是 `codex-cli 0.155.1`，模型 `gpt-6-astra`，网关 `csw-subapi.833233.xyz`；建线程、真实回合、结构化输出、本地图片输入、只读沙箱、MCP 只读白名单工具调用全部打通，bwrap 在 root 下正常。下面的要点已按实测更正。


- **定位**：官方定位是产品内深度集成，自动化建议用 SDK；本方案只让它做深核与将来的对话入口。
- **线程口径**：每个推荐或待核候选一个线程，默认并行 3；首批限 4–8 条、10 分钟时间盒；`developerInstructions` 注入阶段标准、判断框架、该事件的判断结果与缺口；图片先下到线程 `cwd`，回合输入用 `localImage`；回合级超时由采集服务管，超时即 `turn/interrupt`，重试一次再失败向引擎报失败。
- **进程与配置**：采集服务以子进程拉起 `codex app-server`（stdio），独立 `CODEX_HOME=/opt/csw-collector/codex-home`；`model_provider` 指向 sub2api（`wire_api = "responses"`，`base_url` 用 `csw-subapi.833233.xyz`）；`web_search` 关闭；MCP 只挂 csw 只读白名单 9 个工具与本地 `csw_kb` MCP。实测每回合底座：挂 9 个 MCP 工具时约 18.7k token，不挂 MCP 时约 11k。完整配置见实测记录第 3 节。
- **最大的坑**：`approvalPolicy: "never"` 会把需要审批的 MCP 工具调用直接拒绝。正确组合：线程级 `never` + `sandbox: "read-only"`；MCP 服务上 `default_tools_approval_mode = "approve"` + `enabled_tools` 白名单；客户端仍实现三个审批处理器并一律回 `decline`。
- **过程可核**：每条 `item/completed` 原样落盘，随交付物归档到 `trace/`；`thread/tokenUsage/updated` 按 run 汇总。增量事件（`item/agentMessage/delta`、`item/reasoning/summaryTextDelta`）量极大，落盘要过滤。分页历史模式在 0.155.1 上不再阻碍建线程（默认即 paginated）。
- **协议要点（实测）**：`turn/start` **是异步的**，响应立刻返回 `inProgress`，真正的完成信号是 `turn/completed` 通知；`threadId` 在 `result.thread.id`；图片输入格式 `{"type": "localImage", "path": "/绝对路径"}`；**同一线程上一个回合未结束时，起带不同 `outputSchema` 的新回合会被拒**（`ActiveTurnOutputSchemaMismatch`），所以判断步骤若走 app-server 必须一条线程一个回合。
- **硬要求**：读循环不阻塞；只用 stdio、固定版本 0.155.1；`gpt-6-astra` 在 0.155.1 上正常且元数据齐全（`gpt-5.6` 反而会报元数据缺失警告）；Linux 沙箱依赖 bwrap，实测 root 下正常。

> **实现时改了**：协议客户端**自写薄 stdio 客户端**，不 path 依赖 codex 仓库那三个 crate——它们会拖进五百多个 crate、版本号是 `0.0.0` 锁不住，而本地 main 与生产的 0.155.1 也不是同一份。自写的只为用到的六七个类型写 serde 结构，其余用 `Value` 兜底；协议面已对真 codex 0.155.1 验过三项全过。MCP 服务端同理自写，不引 `rmcp`——协议面只有四个方法，传输与 app-server 是同一套。

### 12.2 放哪、怎么跑

- **放 agent 主机，划地盘**：向量服务同机走 `127.0.0.1:8022`，小红书要用这台机上已登录的 Chrome，切换期与 Hermes 并存、切回快。systemd 单元 `csw-collector.service`（`Restart=always`、`EnvironmentFile=/opt/csw-collector/collector.env` 0600、`MemoryMax=4G`、`CPUWeight` 调低）；一个进程管全部，codex 是它的子进程，深核完就停；不拆微服务。
- **数据**：引擎 SQLite 存真相（每天几百行，随 `deploy.sh` 备份）；`/opt/csw-collector/data/lancedb` 起步约 0.2 GB、每天 +8 MB，可重建、每周 tar 到 OSS；`data/images` 每天 80–100 MB，候选图保留 120 天、参考图永久；线程记录与日志保留 90 天。
- **构建与上线**：目标 glibc 2.34，在 Mac 上用 `rockylinux:9` 容器 `cargo build --release`，产物一个二进制加 `web/`；`csw-task/deploy-collector.sh` 照 `deploy.sh`：备份 → 上传 → `systemctl restart` → 等 `/healthz` → 失败自动换回。首次另加：装 codex 固定版本、建目录、写 env、加 nginx 站点 `collector.aworld.ltd`（证书已有）→ `127.0.0.1:8090`。
- **切换与回退（M5 → M6）**：并行期采集服务只跑手动轮不写引擎；切换日开任务驱动、停 Hermes 收集员网关（先确认主网关是不是它）；回退反过来两条命令，五分钟内。Hermes profile 目录原样保留。
- **GPU 分时**：向量入库单线程分批放夜间；白天只做增量与重排。

### 12.3 单点与失败面

| 依赖 | 断了会怎样 | 怎么办 |
|---|---|---|
| csw-agent API | 第 2 步取不到，整轮停 | 重试三次后标失败告警，不用旧接口兜底 |
| 向量与重排服务（单 GPU） | 向量化与召回失败，判断标「对照材料缺」 | 健康检查；只影响当轮；GPU 被占满时同样表现，要定分时 |
| sub2api | 识别、判断、深核全停 | 重试加熔断；备用模型通道（拍板）；总览告警 |
| 引擎 | 接不到单、写不进结果 | 缓存未提交结果，恢复后按幂等键重放 |
| codex 子进程 | 深核失败 | 时间盒；条目仍可登记并写明缺口 |
| agent 主机 | 全停（向量服务、Chrome、Hermes 全在上面） | 最大单点：短期 systemd 自启与监控；中期迁走 jellyfin、es，清镜像 |
| 内存与磁盘 | OOM 或写满 | `MemoryMax`、保留期、磁盘水位告警（85% 已到） |

### 12.4 安全与监控

- 采集服务只持只读 csw key 与收集员角色的引擎 token；写引擎只有登记与交付；不写 csw 库。codex 子进程只读沙箱、只读 MCP 白名单。工作台在 TLS 后、JWT 校验、写操作全审计。向量服务只在本机端口。送往第三方的数据：sub2api（贴文正文与图）、TypeSafe（若启用，正文与图片描述）；Van 群聊原话单独拍板。
- `/healthz` 与 `/metrics`：每步耗时、失败、队列、向量服务延迟、磁盘与内存水位。告警两条线：流程失败经引擎 `fail` 由引擎播报编辑部群；运维告警发开发群。日志与指标可接已有的 Grafana / Loki。
