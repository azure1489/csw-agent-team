# 判断台账反馈八项 · 实施计划（全部实现 → review → 部署）

## Context

2026-09-22 的《情报收集员后台反馈｜判断台账》对第 3 轮判断台账提了八项问题。起因是台账偏重"变化"，六维被当成打勾表；此外还有编造前后对比、把"没读到"当成"没价值"、查重结论自相矛盾、同一产品占多个推荐位、看不到实图、历史偏好没接进判断、缺口不分级这几类问题。

09-23 用户拍板三件事：
- 新六维定义是 **Van 本人认可**的；
- 记忆接入**只送「对象 + 结论 + 理由码」，不送原话**，准则卡只送已确认的；
- **同意定点补读抓外网，但先封内网**。

之后用户要求：全部实现，确认后动工，完成后 review，最后部署上线。

上一版的方案概要在 `docs/情报收集员工作台_判断台账反馈修改方案_20260923.md`（提交 `1366422`）。本计划是在代码勘察之后细化的执行版。

**勘察得到的硬事实**（直接影响设计）：
- **引擎**：写判断台账只校验 `dims` 的六个键名（`engine/intake.go` 的 `validateDims`）。三句话、查重、缺口都是原样存 JSON；`intake_judgements.item_key` 可为空，也没有外键。
  → **引擎表结构与接口都不用改**，只需在 v10 定义里改措辞。
- **`Judgement` 结构**（`core/src/types.rs:374`）的完整字面量散在约 15 个文件里，另外 `seed_demo.rs` 也会被 clippy 编译。本地库 `judgements`（`core/migrations/0001_init.sql:186`）的三句话、查重、缺口列都是 JSON，读回时解析失败会**静默兜底为空**。
- **`inputs_hash`** 不含输出 schema，必须升 `PROMPT_VERSION` 才会重判。
- **`order.rs` 的 `yes_count` 排序在生产里没人调用**：台账按 SQL 的档位加条目键排，交付物按判断输出顺序排。所以"按成立数排序"并没有生效，删掉即可。
- **合并出的事件组**（`judge/src/merge.rs`）只存在内存里：`events` 表、`round_candidates.event_key` 都没人写。判断和登记都是一帖一条（`serve/register.rs:150`），`ItemInput` 里的 brand、product、dedup_note、evidence_url 也都没填。
- **对照材料**（`judge/src/materials.rs:123`）只有 03 决定带正文，其余只给标题，**模型拿不到历史文章正文就判"无关"**，这就是 Dapple Born 那条的根源。`Material` 没有"正文可得"标记；决定和生成稿的 `publish_state` 是空串；上一轮台账在调用处恒传 `&[]`。
- **选题记忆**：本地有 `memory_rules` / `memory_cases`（由 `kb/src/sync.rs:639` 从引擎同步），但**判断提示词里从来没有放进去**。本地表也丢了 brand、title、judged_tier、category、confirmed_at 这几列。
- **SSRF 防护完全没有**：下载器（`harvest/src/download.rs:107`）是默认 reqwest，会跟随 10 次重跳转。`fetch_page` 根本没实现，`features.web_collector` 和 `deepcheck_web_tools` 两个开关也都没人读。csw 接口不返回主页链接，只能用正文里的链接做补读。
- **深核**在登记之后才跑，只往缺口里追加（`finish.rs:451-489`），而且没回写引擎。
- **取图**：图片存为 `blob_dir/ab/cd/<blake3>.jpg`（`download.rs:83`），`media.path` 列没人填，也没有任何接口吐图片字节。`require_session`（`http.rs:115`）只认 cookie，所以同源 `<img>` 能直接用。
- **待核结转**（`core/src/ledger.rs:336`）用的是原始档位，**不看人工改档**（这是个 bug）。概览的档位计数也是原始档位。
- **前端**：维度名、档位名在 Ledger 和 Item 两页各抄了一份；`Ledger.tsx:429` 用了不存在的 `text-danger`；`react-virtual` 已装但没用上。
- **daily_news v9**（迁移 `0040`）的 01 文案里写死了旧三句话「发生了什么变化…和以前有什么不一样」，必须出 v10。
- **测试和构建约定**：测试名用中文句子；`make check` = fmt + `clippy --all-targets -D warnings` + test；`contract.json` 靠 `csw-collector schema -o …` 手动重生成。

## 设计总则

1. **引擎零结构改动**。`dims` 保留六个键名，只换含义。新字段放进收集员本地库，发给引擎时作为 JSON 原样透传。
2. **口径靠代码兜底**：新建 `judge/src/rules.rs` 收纳全部纯函数规则。违例的处理分三种：退回重判一次、代码改档、标红。每一处都留痕进 `check_flags_json`，前缀写「【口径】」。
3. **版本升级**：`RUBRIC_VERSION` 升到 `van-rubric/v2`，`PROMPT_VERSION` 升到 `judge/v3`，旧缓存自动失效。
4. **旧数据兼容读**。旧行里的缺口是字符串数组、三句话是旧键名，读回时用 serde 别名和自定义反序列化兼容，不迁移旧数据。
5. **Van 原话不进任何模型**。补读抓回的正文按第三方内容处理，走 `prompt::fence`，封在不可信边界里。

### W2 · 代码兜底与重判一次（第二、三、四、八项）
新建 `judge/src/rules.rs`，写成纯函数 `apply(j, ctx) -> Vec<Action>`，其中 `ctx` 包含 materials、candidate、是否已重判过。

| 规则 | 条件 | 动作 |

### W5 · 安全抓取与定点补读（第三项 + 封内网）
- **`harvest/src/netguard.rs`**：
  - `is_forbidden(IpAddr)` 覆盖以下地址：

  - `guarded_client(timeout)` 作为公共构造。

- **补读编排**（`serve/round.rs::harvest_and_judge`，`pipeline::run` 之后、`put_judgement` 之前）：
  - **触发条件**：R3 改成待核的；模型给了待核且缺口里有补读路径的；正文命中「link in bio / 主页链接 / 全文 / 官网 / 详见」且 Jev gain ≥ 0.5 的。

  - 进度写进判断步骤的 counts：补读条数、取到条数。

## 风险与约束

- 新提示词和 schema 会让录制回放夹具全部失效，要重录。每轮模型调用增加：重判至多约 10% 的条目，补读至多 15 条，选题综合按组数计。整轮时长要看 r54 的实测；超出预算就先调低 `refetch_per_round`。
- 持续有效的安全约束：
  - 生产动作逐项取得同意，只由主会话执行；
  - Van 原话不送任何模型、不打进会话；服务器上只做只读统计，不读 quote 列；
  - 只用 csw-subapi；
  - 密钥打码；
  - 迁移先在生产库副本上演练。
