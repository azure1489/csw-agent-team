### 踩过的坑，别再踩

1. **别拿 `| tail` 收编译的尾巴**——管道的退出码是 `tail` 的，
   有一次交叉编译实际失败了却被报成成功，拿旧二进制白跑了一轮自检。
   一律写 `cargo ... > /tmp/x.log 2>&1; echo "退出码 $?"`。
2. **后台编译时别改代码**：它会把改到一半的文件编进去，报一个看不懂的错。
3. **外推吞吐按资源占用算**，不按每条墙钟——抽样的尾巴会把后者算高三成。
4. **`anyhow` 的 `to_string()` 只给最外层 context**，看原因要用 `{:#}`。
5. **`cargo fmt` 会重排多行调用**，之后按原文替换就对不上；改前先 `sed -n` 看当前形态。
6. **clippy 的 `-D dead-code` 很严**：写了没人调的 `pub fn` 就过不了 `make check`。
   写一层就把它接起来，别攒着。

### 0.4 判断吞吐（09-22，实测 104 条真实候选）

脚本 `docs/tools/collector_experiments/responses_probe.py`，在 agent 主机上对
`csw-subapi` + `gpt-6-astra` 的 Responses 接口实测。严格 `json_schema`（总方案 §7.4 的
输出，`{}` 占位已展开、每层补 `additionalProperties:false`）**全部返回合 schema 的 JSON，
零解析失败**。

| 配置 | 每条耗时 | 每条入 token | 每条出 token | 429/5xx |
|---|---|---|---|---|
| 逐条 · 3 图 · 并发 8 | 9.7 s | 7292 | 1045 | 1 / 8 请求 |
| 逐条 · 3 图 · 并发 16 | 8.4 s | 7178 | 1120 | **9 / 24 请求** |
| 批量 6 · 3 图 · 并发 4 | 10.0 s | 2310 | 699 | 0 / 4 |
| **批量 6 · 3 图 · 并发 8** | **8.5 s** | **2370** | **780** | 3 / 8 |
| 批量 6 · 0 图 · 并发 4 | 5.4 s | 1421 | 656 | 0 / 4 |

**三条结论：**

1. **吞吐是网关定的，约 8–10 秒一条候选，批量与并发都改不动。** 并发从 8 提到 16，
   9/24 的请求吃 429，墙钟几乎没变——多出来的并发全换成了退避。
   **300 条候选 ≈ 42–50 分钟纯模型时间。**
2. **批量 6 条一请求省三分之二输入 token**（7292 → 2370）、三成输出 token，吞吐不变。
   采用批量是为了成本，不是为了速度。每 300 条约 711k 入 + 234k 出。
3. **单批延迟方差极大：124 s – 405 s。** 客户端超时不能低于 420 秒，重试必须幂等。

**对计划的影响（重要）**：设计决定 5 里「预取轮是缓存不是前置条件，没有缓存整轮也能从零跑完，
只是慢」——现在「慢」有了数字：**光判断这一步就要 42–50 分钟**，首批 ≤20 分钟的目标在无缓存时
不可能达到。**预取轮从「优化」升级为「必需」**；05:30 的正式轮必须是「复用 + 补增量」，
从零跑只能当降级路径，且要如实告诉主编会迟到。

这也让待答的「是否要第二条模型通道」变得实在：再加一条通道大致能把判断时间对半砍。

**顺带验证的两件事：**

- 不发图时，模型**正确地把 24 条全部落成 `pending_check`**（依据：没读到实图）。总方案
  「没读到实图就 pending_check、不因此淘汰」这条硬规则，模型是照做的。这同时说明
  **纯文本判断不是可行的提速路径**——它按定义就判不出结论。
- 网关 25 个模型：`gpt-6`、`gpt-6-astra`、`gpt-5.6`/`-sol`/`-luna`/`-terra`、`gpt-5.4`/`-mini`、
  `gpt-5.3-codex-spark`、`gpt-5.2` 系列、`gpt-image-*`。降级目标 `gpt-5.6-sol` 在册。

| 项 | 实测 | 安全批量 |
|---|---|---|
| 纯文本向量 | 96–118 ms/条 | **≤8**（正文中位 464 字） |
| 图文融合向量（正文 + 1 图） | 458–491 ms/条 | **≤4** |
| 纯图片向量（w_768，约 46 KB） | 384–428 ms/张 | **≤2** |
| rerank 文本 | 127–165 ms/段 | 50 段 8.3 s |

**两条硬约束：**

1. **显存很脆，而且 OOM 会赖着不走。** 22 GB 卡，批 24（1500 字正文）直接 CUDA OOM；
   更要命的是**紧接着的批 1 也失败**——上一次 OOM 的显存没释放，要等它自己回收。
   计划里「文本 ≤32、图 ≤8」只在短文本下成立。实现必须：批量按 token 预算算而不是按条数、
   把 500/CUDA OOM 当可重试并**对半降批**、全部 GPU 调用走**单一队列串行**。
2. **抢卡代价极大。** 向量化与 rerank 并发时两边都被拖到约 4000 ms（单独跑分别是 945 ms 与
   3561 ms），并发不但没有收益还制造了 4 倍的延迟方差。**GPU 调用必须串行**，
   设计决定 5 的优先级队列要落成真正的单通道。

### 0.5 时间预算重算（这是阶段 0 最重要的产出）

把 0.4 与 0.5 的实测代进一轮 358 条候选 / 1871 张图：

| 步骤 | 资源 | 计划估计 | **实测外推** |
|---|---|---|---|
| 取数 | csw API | 约 2 秒 | 约 2 秒 ✓ |
| 图片下载 | 网络 | —— | 约 2 分钟（w_768，中位 46 KB，并发 8） |
| **图片识别** | **模型网关** | 5–7 分钟 | **42 分钟** |
| 向量化（融合 358 + 图 1871） | GPU | 9 分钟 | **15 分钟** |
| rerank（358 条 × 24 段） | GPU | 12–18 分钟 | **21 分钟** |
| **逐条判断** | **模型网关** | 3–5 分钟 | **42–50 分钟** |
| 深核 | 模型网关 | 10 分钟 | 10 分钟（未重测） |

- 网关侧合计约 **95 分钟**，GPU 侧合计约 **36 分钟**。两者是不同资源，**可以流水线重叠**，
  所以一轮从零跑完的下限约 **95–100 分钟**，不是两者相加。
- 对比目标「首批 ≤20 分钟、整轮 ≤45 分钟」：**从零跑差了一倍以上**。

**结论：预取轮是必需的，不是优化。** 01:40 开跑、网关与 GPU 流水线重叠，约 03:15 完成；
05:30 的正式轮只做「按 `inputs_hash` 复用 + 补增量 + 深核 + 登记」。从零跑只能作降级路径，
且必须如实告诉主编会迟到。

**这让「是否要第二条模型通道」变成一个有数字的问题**：网关侧 95 分钟里，识别与判断各占约一半，
两条通道大致能把它砍到 50 分钟。

### 0.6 登录转发（09-22）

`csw-collector auth-probe` 起一个真的 BFF，对本机跑起来的引擎 `adminsrv` 把整条链路走一遍，
**17 项全过**：

- 登录 200；下发 `csw_collector_sid`，带 `HttpOnly`、`SameSite=Lax`，值是不透明随机 id 不是 JWT。
- **引擎的 access 与 refresh 一个都没出现在给浏览器的响应里**（自检直接在响应全文里搜会话内的 token）。
- `/me` 带 cookie 200、不带 401。
- 把会话里的 access 到期时间拨到过去再调 `/me`，**自动续期成功且 refresh 已轮换**（引擎每次都换，
  所以客户端必须接住新的那一枚——`reqwest` 的 cookie feature 刻意不开，自动 cookie store 会把
  「这枚 refresh 属于哪个用户会话」糊掉）。
- CSRF 双提交：缺头挡住、对的放行、错的挡住。`SameSite=Lax` 挡不住表单式跨站 POST，这层不能省。
- 登出 204，之后 `/me` 401，会话真的从存放处删掉了。
- 错口令返回 401 且**不区分「用户不存在」与「口令错」**。
- **van 角色映射生效**：引擎里 `van` 是 viewer，工作台里显示为 `van`，同时保留 `engine_role=viewer`
  让界面能看出它本质是个只读账号。

代码落在 `crates/engineapi/src/admin.rs`（引擎鉴权客户端）与 `crates/collector/src/bff.rs`
（会话、CSRF、角色映射），不是一次性打样——阶段 2C 直接用。会话存放处现在是内存里的
`SessionStore`，阶段 1.1 换成本地库的 `sessions` 表，接口不变。

### 0.7 Jev 三种用法（09-22）

脚本 `docs/tools/collector_experiments/jev_backtest.py`。模型 `jev-latest`。
**金标是真的，不是我标的**：正样本 = csw 里「已生成过文章」的贴文（团队真写过它，300 条池里抽 80），
负样本 = 9/17–9/18 窗口里未被写过的贴文（抽 80）。两边都是 Instagram 原文，同构可比。
全部 340 次调用零失败，输入 67 万 token，**合约 0.028 美元**，300 条初评约 45 秒。

**一 · 六维初评：方向全对，但只能排序，不能淘汰**

| 维度 | 已写过（成立概率中位） | 未写过 |
|---|---|---|
| change | 0.99 | 0.79 |
| use | 0.57 | 0.21 |
| gain | 0.99 | 0.89 |
| compare | 0.57 | 0.33 |
| **explain** | **0.68** | **0.24** |
| **csw** | **0.64** | **0.23** |
| worth（总判） | 0.46 | 0.25 |

六个维度全部朝正确方向分开，`explain` 与 `csw` 分得最开、`use` 次之，`change` 与 `gain` 几乎不分
（Instagram 文案普遍都在宣布点什么、都带点事实）。但总判 `worth` 的阈值扫描很不乐观：

| 阈值 | 已写过的留住 | 整体筛掉 |
|---|---|---|
| 0.12 | 99% | 9% |
| 0.30 | 71% | 43% |
| 0.50 | 46% | 69% |
| 0.70 | 8% | 93% |

**结论：Jev 初评不能当淘汰闸。** 想筛掉一半就得丢掉三成本该写的。这**正面支持了总方案
「每条都判、不设 top K」的口径**——在 0.4 测出判断吞吐是瓶颈之后，用 Jev 砍掉一半候选看着很诱人，
这组数字说明那样做会漏掉真东西。Jev 的位置就是计划里写的：**流式推进的排序键**，不是闸。

排序键该用 `explain` + `csw` + `use` 这三个分得开的维度来建，不要只看 `worth`；具体权重在阶段 4
用更多样本定。**这个排序键只在内部决定「先判哪条」，绝不进台账、绝不显示成分数**——
「不打数字分、无权重」这条口径管的是判断输出，不是内部调度。

**`lower`（七类降低优先级）这个问法失败了**：已写过 0.39、未写过 0.46，几乎不分。
按 TypeSafe 自己的指引，多标签共存时该**一类一个 noul**，不是合成一个。阶段 4 改成七个。

**二 · 同一事件与对照结论：可用，阈值 0.5**

| 桶 | same_event 中位（四分位） | 对照结论分布 |
|---|---|---|
| 跨品牌随机（真负例） | **0.03（0.03/0.04）** | unrelated 28 / same_brand_with_gain 2 |
| 跨账号同品牌 | 0.24（0.03/0.63） | same_brand_with_gain 13 / unrelated 16 / same_fact 1 |
| 同账号同品牌 | 0.05（0.04/**0.97**） | same_fact_no_gain 12 / unrelated 14 / same_brand 4 |

真负例贴在 0.03 且极紧，**误合并的风险很低**；同账号那一桶呈双峰（多数不同事件，少数 0.97 的
确是同一件事），符合直觉。阈值取 0.5 合并即可。对照结论三选一的分布也讲得通：跨品牌随机
28/30 判 unrelated，同账号同品牌多判「同一事实无增量」。

注：**图片哈希在跨账号转载上对不上**（窗口内共享 mediaHash 的组 = 0），所以同一事件不能靠哈希兜底，
只能走向量 + Jev。

**三 · 核对依据：抓编造 100%，但会误伤三成真依据**

把 0.4 实测里生成模型写的依据，配它自己的正文（真依据）或配另一条贴文的正文（张冠李戴）：

| | supported 中位（四分位） |
|---|---|
| 真依据配本条正文 | 0.59（0.15/0.79） |
| 张冠李戴 | **0.02（0.02/0.03）** |

| 阈值 | 真依据放行 | 张冠李戴抓出 |
|---|---|---|
| 0.3 | 68% | **100%** |
| 0.5 | 60% | **100%** |
| 0.7 | 34% | **100%** |

**编造的依据一条都没漏，而且贴在 0.02**，分离得非常干净。真依据只放行 68% 是因为本次只给了正文——
很多依据引的是「第 3 张图」，正文里当然核不到。真实运行时材料里会有识别输出，这一项会上去。
**取阈值 0.3，被标出来的给人看，不自动淘汰**——与总方案 §7.2c「不一致的标出来给人看」一致。

### 阶段 1 · 契约冻结（09-22）

**1.1 core 类型与本地库。** `crates/core/src/types.rs` 定了候选、媒体与识别、五类对照材料、
六维判断、Jev 初评、事件、outbox 的全部值类型。三条口径直接写进类型里，靠测试守住：

- `Judgement::violations()` —— 六维必须齐全且每维有依据；**没读到实图就必须落 `pending_check`**。
- `Candidate::is_image_only()` —— 只取图文的严格判据（类型是图或轮播，**且**媒体里一个视频都没有）。
- `Triage::priority()` —— 排序键只取 0.7 测出分得最开的 `explain + csw + use`，**不看 `worth`**；
  这个值只在服务端决定「先判哪条」，不进台账、不进接口响应。

本地库 `crates/core/migrations/0001_init.sql`，**21 张表 + 1 张 FTS5 虚拟表**。
两条硬规则用库层面的约束兜底，代码漏判时它也拦得住：

- `judgements` 上 `CHECK (image_seen = 1 OR tier = 'pending_check')`。
- `rounds` 上 `UNIQUE(task_id, target_version, trigger)` —— 轮询接口偶尔会把同一条派单读到两次。

外键是真开着的（有测试专门验）；WAL + `synchronous=NORMAL` + 10 秒 busy_timeout。

**1.2 契约导出。** `csw-collector schema -o …/contract.json` 导出 25 个类型的 JSON Schema
（utoipa），前端据此生成 TS 类型，**两边不各写一份**。端点契约写在
`csw-task/csw-collector/API.md`：登录、轮次、台账、采集覆盖、待核结转、知识库与选题记忆、
Van 模式、判断框架、运行设置、运维，每个端点标了最低角色。里面明确写了三条「不做的事」——
不提供改引擎流程状态的接口、不提供按分数排序的接口、不回写图片描述到 csw。

> 与计划的小偏差：完整 OpenAPI（带 paths）要等 handler 落地，阶段 1 先冻**数据契约**
> 与端点清单。解锁 2C 并行需要的就是前者。

**1.3 录制回放层。** `crates/core/src/record.rs`，三种模式 passthrough / record / replay，
模型、Jev、向量、重排四个出网客户端共用。

- 键 = 规范化请求哈希，**图片换成 `blake3:<hex>`**：20 万字符的 base64 压到 200 字节以内，
  夹具从几十 MB 降到几十 KB，同一张图重下多少次键都一样。
- 键序无关（对象按键排序后再哈希），但**正文改一个字键就变**——该重录就得重录。
- **回放未命中就是失败，绝不静默穿透。** 悄悄去调真接口的回放层等于没有回放层：
  测试会时快时慢、时对时错，而且会偷偷花钱。

### 2B · 引擎运行面客户端（09-22）

`crates/engineapi/`：接单、心跳、报失败、登记 items / sweeps / judgements、自查、
历史决定、一步式提交。三条实测规矩长在客户端里，不靠调用方记得：

- **`Idempotency-Key` 只对 POST 生效**，PUT 不带（引擎靠 `UNIQUE + ON CONFLICT`）。
- **`idempotency_in_progress_or_uncertain` 不重试**，抛成专门的错让上层去对账。

- **心跳不带幂等键**：`ack` 本来就该能重复调，带了第二次就被幂等层挡回来。

另加：判断台账自动分批到 200（一轮三百多条，调用方不该操心批次）；
提交的幂等键从 zip 内容派生（重试必然同键，内容变了必然是新键）；
429/5xx 指数退避加抖动，4xx 业务冲突不重试。

**契约测试两层，8 + 1 项全过：**

- **wiremock** 造真引擎难造的情形：429 连发后成功、409 只发一次、幂等未知抛专门的错、
  心跳不带键、450 条自动分三批、没见过的状态不让整次接单失败（引擎以后加状态时
  收集员不该整轮停摆）。
- **对真引擎二进制**（`contract_live.rs`）：起临时库 → 迁移 → 签 token → 触发一期 →
  跑 `bin/server`，然后接单、取作业标准、心跳三次、上报 `tool=csw_api` 的采集轮、
  上报判断、验证「没读到实图落非待核档被拒」、跑自查、查历史决定。
  引擎二进制不在就跳过，**其余任何失败都会炸**——不把「触发失败」误报成「没装引擎」。

> 这条测试当场就抓到一个真错：触发返回是扁平的 `{"run_id": N}`，不是我假设的
> `{"run": {"id": N}}`。mock 发现不了这种事，因为 mock 是照我的假设写的。

顺带修了一个会在生产炸的坑：reqwest 以 `rustls-no-provider` 接入，**建 Client 前必须先装
crypto provider，否则直接 panic**。现在 `core::ensure_crypto_provider()` 用 `Once` 兜底，
两个客户端构造函数里都调——靠每个入口自觉记得是靠不住的。

### 2B · 采集的四个零件（09-22）

**csw 客户端**把 0.3 查出的四条接口事实写进代码：路径前缀 `/api/v1`；窗口只按
`date_posted` 过滤，所以**取宽 7 天再本地按 `ingestedAt` 收口**；`/accounts` 的 `total`
是页数、`records` 才是条数；单页 50 条。线上版本落后于本地 main，`tagList` /
`hashtagList` 与图片描述一律当可缺——标签补丁部署后自然就有，代码不用改。
点赞这类字段有时是字符串有时是数字，两种都收。

**图片下载**走 OSS 的 `image/resize` 直接要缩略图（少一份图像库依赖也省带宽），
按内容哈希存盘天然去重，分两级目录（一期一千多张、三个月十几万个文件，平铺会卡）。
个别失败不拖垮整批——失败那张标 `failed`，候选照走，只是它的 `image_seen` 会是 false 落待核。

> 测试抓到一个**真并发 bug**：跨账号转载同一张图时哈希相同 → 临时文件名相同 →
> 先完成的把文件改走，后一个 `rename` 就 ENOENT。一期 1871 张图里转载很常见，
> 这在生产一定会发。改成临时名每次唯一，目标已存在就用别人那份。

**向量客户端与模型客户端都放在 `core`**，理由是同一条：**并发上限是全进程的**。
`harvest` 要向量化、`kb` 要重排，各持一个客户端就等于又并发了（0.5 实测并发让两边都慢
4 倍）；识别与判断走同一个网关，各持一个就等于把并发翻倍、全换成 429（0.4 实测
并发 16 时 24 个请求里 9 个吃 429，墙钟几乎没变）。

- 向量：入参是扁平数组，纯文本放字符串、图文融合放 content-part 对象数组（裸字符串放内层会 400）；
  **按重量分批**而不是按条数（图比文本贵一个数量级）；**OOM 对半降批并给显存回收时间**——
  OOM 会赖着不走，紧接着的小批也会失败；降到单条还 OOM 就如实报错，不吞。
- 模型：默认并发 8、超时 420 秒、批量 6，全部照 0.4 实测；同网关内模型降级；
  **每日 token 预算熔断**——一轮识别加判断约 290 万输入 token，一次重试风暴能在没人看着的
  凌晨把一个月预算烧完。

**图片识别**（`harvest::recognize`）：每批 ≤6 张，结构化输出六个字段。
**返回条数与图数对不上直接报错**，不将就——下标错位会让「第 3 张图显示…」这类依据全部指错地方。
提示词版本写进 `PROMPT_VERSION`，与 `media_descriptions` 的 `(blake3, prompt_version)` 唯一键配套：
改提示词不改版本就不会重算。

### 2B · 采集器与四段流水线（09-22）

**采集器 trait**：只负责取候选并归一，下载、识别、向量化由流水线统一做——
加新采集器不用管后面三段，也不该管。内置 `CswWindow`（必扫）、`VanLinks`、
`Disabled`（小红书 / 网页 / 自定义三层）。

三处刻意的设计：

- **`Disabled` 做成一个类型，不是编排里的 `if`。** 开关状态要出现在采集轮里，
  结果记 `partial` 并写明「未启用」——否则「没扫」与「没开」在台账上看着一样。
- **Van 补的链接取不到就报失败**，不悄悄少一条。当期采用的常常全部来自这里。
- **必扫采集器失败就停下告警，不用旧接口兜底**——兜底会把「没去找」伪装成「没找到」。

**四段流水线**（取候选 → 下载 → 识别 → 向量化）：总方案刻意把这四段合成一步。
分开会出一种很难查的状态——候选进了库、图还没下、判断却已经开始，
于是「没读到实图」被当成了「这条没价值」。

- **计数全部由代码算**，不由采集器自报（`found` 用采集器报的接口返回数，
  `fetched_unique` / `in_window` 由代码去重与收口后数）。让实现方自己填这几个数，
  等于让它自己给自己打分——而它们正是 `intake-check` 的对账依据。
- **有一张图没识别成功就不算读到实图**（`Prepared::image_seen()` 为 false），
  判断那一步据此落待核。
- **融合向量的入模文本把图片描述也拼进去**：很多贴文正文只有一句话加一串话题，
  真正的信息在图里——只用正文算向量，检索会找不着它。
- 向量化失败**不阻塞判断**：没有向量只是检索差一点，不是「这条不能判」。

harvest 26 项、core 33 项、engineapi 9 项测试全过。

### 2B · M1 复跑：并发修复与耗时拆解（09-22）

**第一次复跑**（`ca5622f` 的二进制）：每条 **71.5s → 13.5s**，外推一期
**426 分钟 → 80.7 分钟**。取数仍是 358 条 / 1871 图，识别覆盖 100%，读到实图 16/16。

80.7 分钟仍高于预期的 40–60 分钟，所以给流水线加了阶段计时——**把网关时间与
GPU 时间分开记**。两者是不同的资源，混成一个总数就看不出该往哪儿加通道。

**第二次复跑**（带计时）：

| 项 | 实测 |
|---|---|
| 候选 / 图片 | 16 / 95 |
| 墙钟 | 236.9s（每条 14.8s） |
| 下载 | 0.5s（统一做，几乎不占时间） |
| **网关占用合计** | **832.8s → 有效并发 3.5（上限 8）** |
| **GPU 占用合计** | **49.0s → 占用率 21%** |
| 外推一期 | 88.3 分钟 |

结论一目了然：**不是 GPU 瓶颈**（才 21%），而是**网关的闸门没用满**
（3.5 / 8）。按满并发算，墙钟应是 832.8 ÷ 8 ≈ 104 秒，外推一期约 **39 分钟**。

原因是一条候选内部的图片批次**仍是串行的**（`for batch in refs.chunks(6)`）。
候选之间的图数很不均匀，一个二十图的轮播要连打四次；到了尾部它独占墙钟，
其他槽位全空着。已改成批级并发，每条候选自己最多占 4 个（全局信号量是 8，
留一半给别的候选，免得一个大轮播把闸门占满）。**待第三次复跑验证。**

> 值得记一笔的是，这个缺陷是**那两个比值指标**照出来的。
> 只看「每条 14.8 秒」看不出问题出在哪；
> 「网关有效并发 3.5 / 上限 8」和「GPU 占用率 21%」两个数摆在一起，
> 答案就只剩一个。加这两个计时器花了二十分钟，省下的是好几轮瞎猜。

**第三、四次复跑**（批级并发 + 大样本）：

| | 16 条（第三次） | **64 条（第四次）** |
|---|---|---|
| 图片 / 向量 | 95 / 111 | **376 / 440** |
| 识别覆盖 | 100% | **376/376（100%）** |
| 读到实图 | 16/16 | **64/64（100%）** |
| 墙钟 | 176.5s（每条 11.1s） | **655.6s（每条 10.3s）** |
| 识别段平均在飞 | 4.9 条（槽位 8） | **5.2 条** |
| GPU 占用率 | 37% | **38%** |
| 单条识别 中位 / 最慢 | —— | **47.0s / 152.0s** |
| 单条图数 中位 / 最多 | —— | **5 / 20** |

**外推口径改了，这是这一轮最该记住的事。** 原来按「每条墙钟 × 358」算，
16 条的样本外推出 88.3 分钟、64 条外推出 61.3 分钟——**同一套代码、同一批数据，
只因为样本大小不同就差了 27 分钟**。原因是抽样里最慢那一条（152 秒）占墙钟的比重极大，
而它在大批量里只有一条、会被摊薄；按条数复制 358 遍就是把这段尾巴算了 358 次。

改成按资源占用算：**网关总占用 ÷ 槽位、GPU 总占用 ÷ 1（它是串行的），两者可重叠取大者**。
这个口径下 16 条与 64 条的外推是一致的，64 条给出 **39.7 分钟**。

> 「按每条墙钟」那一行仍然打印出来，但标着「抽样时偏高」。
> 两个数摆在一起，比只给一个「正确」的数更有用——它让读的人知道差距从哪来。

**真数要跑 `--full`。** 39.7 分钟是外推，不是验收。

### 6 · codex 协议自检：三项里两项通过，第三项抓到真错（09-22）

写了 `csw-collector codex-probe`，对 agent 主机上**真的** codex 0.155.1 跑：

| 项 | 结果 |
|---|---|
| 握手 `initialize` + `initialized` | **通过**（253 ms） |

缺了就在拉起时 warn——而不是让它变成回合里一句隔着协议很难看懂的报错。

> 这正是写这个自检命令的理由：协议要点是从实测记录抄来的、客户端是新写的，
> 中间那条缝只有对真二进制跑一遍才看得见。`contract_live` 对引擎做过同样的事，
> 当场抓到过「返回是扁平的 `{"run_id": N}`」那个错。
>
> 修完复跑**三项全过**，协议这条路整条验通了：`result.thread.id` 的位置、
> `turn/start` 异步 + 等 `turn/completed` 通知、`item/completed` 里 agentMessage
> 的字段名（`item.text`，猜对了）、增量过滤、环境放行。
> 握手 244 ms、建线程 107 ms、一个纯文本回合 5.5 秒——与实测记录的 4–7 秒吻合。

### 6 · 预取轮接进编排（09-22 晚）

**计划里写的是「按 `harvest_hash` 与 `inputs_hash` 查 `rounds::reusable_from`」，
实际做不到，改成了按条复用。** 原因很简单：预取轮 01:40 取前 24 小时、
正式轮 05:30 也取前 24 小时，两个窗口不是同一个，**步级指纹永远对不上**。
而条级的绝大多数都对得上——重叠的那二十小时里，候选一条没变。

为此先补了两处「表建了却没人写」的缺口：

| 新模块 | 写哪张表 | 为什么非它不可 |
|---|---|---|
| `core::media` | `media` / `media_descriptions` | 描述只留在内存里的话，这趟网关钱下一轮还要再花一遍 |
| `core::mirror` | `task_mirror` | 01:40 没有派单，作业标准只能从上一次的派单里取 |

再加两个缓存接口，各自只回答一个问题：

- `harvest::pipeline::Descriptions`：这条候选的图识别过吗。
  **判据是「每一张图的 blake3 都有描述」**，不是「有几条描述」——
  贴文被编辑换掉一张图时数量可能还一样，而那正是最该重识别的情形。
- `judge::pipeline::Cached`：这条判过吗。判据只有 `inputs_hash` 一个，
  实现方不许再加宽松条件：它是唯一一道拦着「换了东西还在用旧结论」的闸。
  拿回来的结论还要再过一遍 `violations()`，不合契约的宁可重判。

一轮命中缓存时，各段的账：

| 这一段 | 命中时 | 说明 |
|---|---|---|
| 识别（模型网关） | **整段跳过** | 整轮网关时间的大头 |
| 每图向量（GPU） | **跳过** | 整轮 GPU 时间的大头（约 3.4 秒/条） |
| 融合向量（GPU） | 仍然算 | 约 0.5 秒/条，检索要用它 |
| 下载 | 仍然下 | 图不在内存里，而且 blake3 要靠它算出来 |
| 初评 / 合并 / 核对（Jev） | 仍然问 | 便宜，且排序要覆盖全量 |
| 逐条判断（模型网关） | 作业标准没变才跳过 | 主编改了派工单备注就重判 |

几个刻意的决定：

1. **作业标准存「拼好的那一整段」，不存三段**。它进 `inputs_hash`，
   预取轮与正式轮拼出来的必须一字不差；分两处拼迟早会分叉，
   而分叉的表现只是「复用永远落空、每天慢四十分钟」，**不报任何错**。
2. **预取轮与正式轮走同一段代码**（`round::harvest_and_judge`），同上理由。
3. **预取轮的结论不进「上一轮台账」**（`prior_ledger` 排除 `kind='prefetch'`）——
   它是同一天凌晨为这一轮预先算的，当对照材料等于自己给自己作证。
4. **预取轮失败不往引擎报**：引擎根本不知道有这一轮。只收轮、记一笔，
   并在日志里写明「正式轮要从零跑，会慢四十分钟」。

顺带堵上接续点里标的那个会出错的地方：`start_round` 现在按 `stage_code` 岔开，
不是 `intake` 的**如实向引擎报失败**（核过引擎源码，`CanFail` 允许 `dispatched`，
不必先接单），而不是拿 01 的十步去跑 05／11 交出一份文不对题的台账。

**发现的一处浪费**：每张图的向量一直在算，却没有任何地方存、任何地方用
（`Prepared::image_vectors` 只在 M1 里被数了一下）。按 M1 的数字，
它是整轮 GPU 时间的大头。命中缓存时现在跳过了；**没命中时仍然在白算**——
等 11 选图包要用图向量时，一并把「存进 LanceDB + 命中时读回来」做掉。

### 6 · 工作台写接口（09-22 夜，阶段 6 收尾）

五个写接口，全部过 CSRF、全部留痕、**全部不干活**：

| 接口 | 做什么 | 最该记住的一条 |
|---|---|---|
| `POST /api/rounds/:id/judgements/:key/override` | 改档 / 标待核 / 捞回 | 另存一行，**原判一个字不动**；理由必填 |
| `POST /api/rounds/:id/first-batch` | 指定深核首批 | 指定的不看档、排在自动挑法前面；总数仍受上限管 |
| `POST /api/van/marks` | Van 勾选 | 不给轮次就落到**当期派单轮**，不落到凌晨那轮预取 |
| `POST /api/rounds` | 手动开轮 | 只排队；窗口解析不了**当场** 400，不排进队等四十分钟才发现 |
| `POST /api/rounds/:id/steps/:step/rerun` | 重跑 harvest 或 judge | **登记与提交不动**；用那一轮当时的作业标准 |

三个决定：

1. **HTTP 不干活。** 开一轮四十分钟，请求等不了。写接口只往新建的
   `work_queue` 写一行就返回，常驻循环每次 tick 取一件来做——它才持有
   模型与向量客户端、才持有那个唯一的写连接。失败原因写回 `work_queue.note`，
   那一行就是页面上「为什么没成」的唯一来源；只写日志等于只有能 ssh 的人看得见。
2. **「重跑一步」= 把那一步的缓存关掉。** 复用已经做在条这一级，没有
   「把某一步作废」这回事——关掉缓存才是真正的重算。`harvest` 连识别一起重来，
   `judge` 只重判。登记与提交不在其列：引擎已经收到的台账要改只能走补件。
3. **生效档与原判分两个字段。** `tier` 是模型判的，`effective_tier` 是现在显示的。
   台账的筛选与排序按生效档——主编捞回一条之后台账还把它排在不推荐组里，
   那次捞回就等于没发生。

角色三档：`operator`／`superadmin` 全能；`van` **只能勾选、改不了档**
（进不进评选由主编代录并附原话）；`viewer` 一个写都不行。
十一条 HTTP 层测试守着：没会话 401、CSRF 不对 403、viewer 全 403、
van 改档 403 勾选 200、改档后原判不动且留痕有人名。

与 `API.md` 的三处对照已经写进那份契约：`recover`（硬性排除还没做，
现在捞回就是改档）、`cancel`（未实现）、`rerun` 的语义（只认两步）。

目标机跑不动」的风险——交叉编译那一关已经吃过几次亏。问不出来当「不知道」，

  其实缺文件的备份。备份自己也先看磁盘水位，盘紧时不雪上加霜。
- **开发群告警**（`core::alert`，默认关，地址只从 env 走）。

  「预取轮没跑成」——**这些只有我们自己发现得了**，不发出去就只有能 ssh 的人看得见。

  一律不进告警，第三方机器人的消息记录不在我们手里）、发不出去只 warn 绝不让活停下。

### 一个流程上的教训：别拿 `| tail` 收编译的尾巴

有一次交叉编译实际上失败了（它撞上了我正在编辑的 `mcpsrv`），
但因为命令写成 `cargo zigbuild ... 2>&1 | tail -3`，管道的退出码是 `tail` 的，
任务被报成「成功」。结果是拿着一个旧二进制去跑自检，白白多跑一轮。

以后编译一律写成 `cargo ... > /tmp/x.log 2>&1; echo "退出码 $?"`。

## 3.5 实现时要记住的技术细节（勘察/实测得到，代码里不重复解释）

- **jieba 分词器 lancedb 已默认启用**，不需要开任何 feature（lancedb 对 lance-index 声明了
  `tokenizer-jieba`）。词典放 `$LANCE_LANGUAGE_MODEL_HOME/jieba/default/`：主词典默认叫
  `dict.txt`，同目录的 `config.json` 用 `{"main": "...", "users": ["..."]}` 指定主词典与
  **自定义词典**——品牌别名表正好落在 `users` 里。不设环境变量时默认目录是
  `<data_local_dir>/lance/language_models`。
- `FtsIndexBuilder` 就是 `lance_index::scalar::InvertedIndexParams`，用
  `.base_tokenizer("jieba/default")` 选分词器；`"jieba"` 会自动补成 `"jieba/default"`。
- LanceDB 的 `create_table` 收 `Box<dyn RecordBatchReader + Send>`（`RecordBatchIterator`
  本身不实现 `Scannable`，要装箱）；`nearest_to` 收切片不收 `&Vec`。
- arrow 只从 `lancedb::arrow::{arrow_array, arrow_schema, …}` re-export 取，别自己声明
  arrow 依赖——版本错一位就是一堆 trait 不匹配。
- 开发机的 rust 宿主三元组是 **x86_64-apple-darwin**（不是 arm64）。
