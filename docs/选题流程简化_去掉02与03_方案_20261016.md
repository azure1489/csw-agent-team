# 选题流程简化：去掉 02 价值初筛与 03 选题方案（daily_news v11）

> 2026-10-16 用户确认。本页是本次改动的接续锚点：每完成一步更新第 6 节。

## 1. 决定（用户 10-16 逐条确认）

1. 研究员的判断归 01：条目状态由 01 落定（推荐 → shortlisted + primary，备选 → shortlisted + alt，不推荐 → dropped + 理由码，待核 → pending_check）。
2. 01 主编闸维持只核格式（五项清单），内容意见写在通过意见里——读者从研究员换成 Van。
3. 保留阶段编号：02、03 空号，其余阶段名与存储路径不变。
4. 待核在 01 内闭环：**有报道潜力的**待核在 01 定点深核完再交（不是全量深核——一期待核常有一两百条）；其余如实留在待核栏，Van 不选，由主编之后用条目决定标继续研究或留下期。
5. 选题研究员完全下线（token 吊销、profile 停用、bot 移出群；roles 表记录保留供历史引用）。
6. Van 选题挪到 01：01 = 主编格式核对 → Van 选题（主编代录，末闸带 topic_approve + items），之后直接 04 / 05 / 06。
7. 01 一次交齐，取消「首批 + 补件追加批次」：01 补件会把 04 / 05 / 06 已开工任务全部标「补件待返工」（`supplement.go` 不按条目过滤）。Van 批准后加题一律走条目补批接口。
8. 「给 Van 的选题单」由工作台在 01 交付物里生成，主编不再另写选题方案。

## 2. 新流程

```
01 情报逐条（情报收集员 · 主编格式核对 → Van 选题，主编代录）
  ├→ 04 公众号写作（逐条）  ┐
  ├→ 05 配图与素材核（逐条）┴→ 07 内容整合稿（主编）
  └→ 06 版式与模板准备 ─────────→ 08 完整审核稿（Van 终审）
08 之后不变
```

## 4. 上线顺序

1. 引擎与文档本地完成、测试、提交。
2. 工作台改动 + 本地演练验证（含一次交齐耗时实测）。
3. deploy.sh 部署引擎（自动备份），v11 为 draft。
4. 部署工作台（确认空闲、先备份）。
5. **激活前同步 agent 主机**：SKILL.md 3.12.0 与 editor / collector / reviewer bootstrap 下发到各 profile（主编是 01 Van 闸的代录人，跑旧 bootstrap 会去等不存在的 03；10-10 起 profile 就未同步）；同时把生产引擎的 `skill_min_version` 升到 3.12.0（生产 config.yaml `server.skill_min_version` 或 `CSW_SKILL_MIN_VERSION`），让没换版的 agent 不开工而不是按旧协议干活。
6. 次日 06:00 开期前激活：`adminctl workflow activate daily_news 11 --confirm 11 --reason "去掉 02/03"`。
7. 观察 v11 首期：01 一次交齐 → 主编格式核对 → Van 选题代录 → 04 / 05 逐条、06 就绪；反馈带出 stage:topic 历史原话；01 耗时在时限内。
8. v10 期次全部走过 02 后：吊销研究员 token、停 researcher profile、bot 出群（agent 主机其余 skill 已在第 5 步同步）。
9. 群通知 @主编 @Van。

回滚：后台重新激活 v10，并把 `skill_min_version` 降回原值（3.12.0 的 SKILL 只描述 v11）；token 最后吊销，所以第 8 步前回滚零代价。

注意：仓库文档（全流程、验收标准、手册、生产约定、SKILL）在第 1 步就按 v11 写了，**生产在第 6 步激活前仍是 v10**。激活后用生产库再跑一次 `gen_stage_docs.py` 核对无差异；`docs/workflows/` 的 YAML 导出只到 v7，与本次无关，如需对齐另用 `wfctl export` 补。

## 5. 风险与观察点
- Van 读选题单的负担：推荐多时选题单变长，首期后问 Van，必要时只列推荐前 N。
- 主编编辑判断变薄：建议头两周主编在通过意见里写「我会选哪几个」供 Van 对照。
- 01 补件波及下游：写进主编手册与交付规范，加题走条目补批。
- 01 一次交齐的耗时：不能再先交首批，整期判完才提交；第 2 步实测，超 40 分钟或逼近 07:15 就先调时限或收窄深核范围。
