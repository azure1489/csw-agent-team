## 0. 已拍板（09-23 用户）

| 事 | 决定 |
|---|---|

核心目标（反馈原文）：让系统更准确地找到值得推荐给中国户外潮流读者的内容，减少 Van 重新筛选、补资料、解释和催促。

## 1. 总体做法

- **引擎零改动**。引擎写判断台账只校验 `dims` 的六个键名（`engine/intake.go` 的 `validateDims`），三句话、查重、缺口都是原样存 JSON。所以六维**保留键名、只换含义**，其余字段在收集员侧改结构。
- **口径不靠模型自觉**：每一条「不许这样判」都配一条代码检查（`judge/src/check.rs` 同层），违例就改档或亮红，不只写进提示词。
- 版本号：`RUBRIC_VERSION` → `van-rubric/v2`，`PROMPT_VERSION` → `judge/v3`，旧的判断缓存经 `inputs_hash` 自动失效。
- 下游读台账的地方要同步改：交付物 `deliver/src/intake.rs`、`trace.rs`，登记 `serve/register.rs`、`write.rs`、`finish.rs`，前端 `Ledger` / `Item` / `Van` / `Pending`，`contract.json` 与 `types.ts`，`seed_demo`。

## 2. 逐项修改

### 一、六维换成 Van 认可的定义

| 键名（不变） | 新含义 | 旧含义 |
|---|---|---|
| `change` | **具体看点**：最值得报道的具体事实、变化或角度；可以是改款，也可以是有依据的设计、文化、历史、生活方式内容，不强求新品 | 具体变化 |
| `use` | **与读者有关**：与中国户外潮流爱好者的使用、穿搭、审美、兴趣、生活方式的联系，不限于功能 | 使用关联 |
| `gain` | **值得推荐的价值（核心）**：为什么值得推荐给中国户外潮流读者，看完能得到什么 | 信息增量 |
| `compare` | **差异与背景**：同类、历史、品牌背景、既有做法，不强求上一代对比 | 比较参照 |
| `explain` | **报道角度与依据**：CSW 抓哪个具体角度、哪些事实撑得住、能讲到什么程度；不要求造趋势 | 可解释性 |
| `csw` | **CSW 适配度**：结合实际采用 / 否决案例说明，不能只因出现露营、户外、旅行等词就判符合 | CSW 视角 |

改动点：

- `judge/src/rubric.rs`
  - 核心问题改为「这条值不值得推荐给中国户外潮流读者？凭什么？」；
  - `DIM_ANCHORS` 换成上表；
  - 写入「中国读者价值不等于国内买得到、去得了」及三个例子（店铺开业、日本限定、海外活动）；
  - 写入「参数、价格、发售日期齐全不证明价值；品牌知名或国外发布不自动推荐」；
  - 写入四问区分：跟谁有关 / 为什么值得看 / 具体讲什么 / 为什么适合 CSW 来讲。
- 定档规则（提示词写明，代码检查兜底）：
  - **推荐必须 `gain=yes` 且依据非空**；`gain` 不成立的，不管其余几项成立，最高给「备选」。代码检查违例改档，并在台账标「按核心维度改档」。
  - 六维不是打勾表，不按成立个数定档。
- `judge/src/order.rs`：现在同档内按「成立维度数」排序，**改掉**。改为按档 → `gain` → Jev 初评的 gain 概率 → 相对热度。
- **新增「制作条件」一组**（输出新字段 `readiness`，与选题价值分开记，不参与定档）：
  - 事实可靠性（有原始来源 / 仅转载 / 仅品牌自述）；
  - 图片可用性（有可作配图的实图几张）；
  - 查重状态（见第四项）；
  - 资料完整度。
- Jev 初评 `judge/src/triage.rs` 的 `dim_questions` 六个问题按新定义重写；「降低优先级七类」里与新口径冲突的一并核（如「只能说好看」保留，「必须强行拔高成趋势」保留）。
- 前端维度名称、Van 模式同步改。

### 二、不许为「变化」编前后对比

- 三句话改成：
  - `what`：这是什么；
  - `why_worth`：为什么值得看；
  - `grounds`：依据是什么。

  原来的 `what_changed` / `how_different` 这两个字段名本身就在逼模型找变化。
- 新增字段 `novelty`，三选一，并附依据：
  - `existing_feature`：产品现有特点；
  - `evidenced_change`：有证据的新变化，**必须指明旧款 / 前代依据出自哪里**；
  - `explainable_design`：值得解释的设计或文化内容。
- **代码检查**：看点、三句话、推荐理由里出现「从……变成 / 改为 / 升级为 / 告别……」这类句式，而 `novelty` 不是 `evidenced_change`，或其依据为空，就退回这一条重判一次；重判仍违例，就标红并把该句替换为「（无旧款依据，已删）」。SML 磁吸包、norbit 两条作为回归样例。

### 三、区分「价值不足」和「关键资料没取到」（Hyperlite）

- **代码规则**：`unanswered=missing_material`，或缺口里有「影响判断」级的「未取得全文 / 外链未读」，却给了「不推荐」的，**一律改为待核**，并生成补读任务。
- **定点补读**（用户已同意，先做安全前提）：
  1. **先补安全**：新写 `harvest/src/fetch.rs` 安全抓取器。
     - 只允许 http / https；
     - 先解析域名再**钉 IP 连接**，每一跳重定向都重新检查；
     - 封掉以下地址：回环、私网、链路本地、CGNAT、云元数据地址（169.254.169.254 等）、IPv6 对应段，以及本机 `8022` / `8090` 端口；
     - 限大小（2 MiB）、限时（15 秒），只收 `text/html` 与图片。

     现有的图片下载器 `harvest/src/download.rs` 同样接上这道封锁（进度文档里挂的「图片下载器不封内网」一并结掉）。
  2. **补读来源**：正文里的链接；正文写了「主页链接 / link in bio / 全文见官网」的，取账号资料里的主页链接（要先核实 csw 接口是否返回账号主页链接；不返回就只用正文链接，并如实写「外链地址未知」）。
  3. **触发条件**：只对「有明确报道潜力」的补读，即 Jev 初评 gain ≥ 0.5，或模型给了「待核」且写明补读路径。不对所有弱题无限补证。**每轮上限 15 条**。
  4. **补读后重评**：抓到的正文加入候选材料，重跑这一条判断；没抓到就留待核，缺口写明「已尝试：抓取 某链接，结果：某状态」。
  5. 抓取器**不进深核的 codex 白名单**（codex 那边的 `fetch_page` 仍默认关），由收集员进程自己调用。

### 四、查重结论必须与证据一致（Dapple Born）

- `comparison.verdict` 加第四档 **`unconfirmed`（查重未确认）**。
- **代码规则**：
  - 命中的历史条目正文缺失，或只有标题，就不许给 `unrelated`，强制改为 `unconfirmed`，并记一条「影响判断」级缺口。
  - 命中来源只有「生成稿」时，**不许给 `same_fact_no_gain`**：生成稿只能帮着复用资料，不是「近期已发」的证据。
- 输出结构扩成：
  - `hits[]`：每条包含命中的文章标题与链接、发布状态（`published` 正式发布 / `draft` 已推草稿箱 / `generated` 仅生成稿）、发布日期、**具体重复了哪条事实**；
  - `note`。
- `judge/src/materials.rs` 给每条对照材料带上发布状态与「正文是否可得」，模型写的和代码检查都以这个为准。

### 五、逐帖之外形成「选题」（SOUTH2 WEST8）

- **先查因**：上服务器看第 3 轮这三条的向量相似度，以及有没有送去问 Jev「同一事件」，确认是没合上，还是合上了仍逐帖占位。
- **合并补一道**：现在只靠向量粗筛（≥0.70）再问 Jev「同一事件」。另加「**同品牌键 + 同产品**」一路：由代码按品牌键把同一品牌的候选配对，再用 Jev 选择题问「是否同一款产品 / 同一事件」，两路取并集。
- **选题层**（本地新表 `topics`，每轮一套）：
  - 一个选题 = 一个事件组；
  - 汇总组内各帖的原文、图片、证据；
  - 标出哪些是重复信息、哪些是某帖新增的（新增内容由模型逐帖列出，代码核对确实出自该帖）；
  - 真正不同的报道角度或后续变化，单列成另一个选题。
- **定档与统计**：
  - 选题档位取组内判断的最高档，依据取组内全部；
  - 台账和总览里「推荐贴文数」和「独立选题数」分开显示。
- **台账页**默认按选题展示，展开看组内逐帖；逐帖台账原样保留。
- **登记进引擎**：一个选题登一条 `run_items`，组内其余贴文写进该条的附证链接；逐帖判断仍全部写进 `intake-judgements`，行数对账不受影响。

### 六、Van 直接看图、快速理解对象

- **后端**：加取图接口 `GET /api/media/{blake3}`，含缩略参数。
  - 需要登录会话；
  - 只从图片目录按 blake3 取，路径由代码拼，不接受外部路径；
  - 带 `Cache-Control: private`。
- **列表页**（台账、Van 模式）每行显示：代表图缩略（选「可作配图」的第一张）、品牌、**具体对象**，再加一句推荐理由。
- **标题规则**：输出的 `look` 改名为 `headline`，格式「具体对象｜一句推荐理由」，限 40 字，不写分析长句。
- **详情页按这个顺序排**：
  1. 图集（点开看大图）与原文、译文；
  2. 发布时间；
  3. 关键缺口（只列「影响判断」级）；
  4. 查重结果；
  5. 推荐理由与三句话；
  6. **默认折叠**：六维依据、制作条件、热度、图片描述表、模型调用等技术记录。

### 八、缺口分级，落实下一步

- `gaps` 从字符串数组改成对象数组：

  ```json
  {"level": "decision | production | boundary",
   "what": "缺什么",
   "owner": "collector | editor | van",
   "tried": "已尝试什么",
   "next": "下一步"}
  ```

  - `decision`（影响选题判断）：产品身份、关键变化、报道价值无法确认。**只有这一级能让条目落待核。**
  - `production`（影响成稿）：必要规格、关键图片、时间信息缺失。**不影响档位**，随条目转给写作阶段。
  - `boundary`（表达边界）：品牌声称的性能未经独立实测等。**不是缺口任务**，只作写作提醒。
- **规则写明**：图片没拍清全部结构，但可靠正文已说明的，不算缺口。
- **代码检查**：
  - 待核条目必须至少有一条 `decision` 级缺口；
  - `owner=collector` 的缺口必须写 `next`；
  - 缺口能由补读解决的，自动进第三项的补读队列，并把结果回写 `tried`。
- **待核结转页**逐条显示：对象（配缩略图）、缺什么、由谁处理、已尝试什么、下一步、挂了几轮，不再只挂一句「补齐后重跑」。
- `owner=editor` / `van` 的待核在总览亮提示，不用等 Van 催。
